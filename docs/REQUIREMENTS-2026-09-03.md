## 一、地图编辑器：暂停 + 自由移动（已拍板，风险低，优先做）

1. **编辑时游戏不运行**：进入地图编辑器（不管是弹窗 `MapEditorDialog.js`
   还是主画面工具条 `MapEditorBoardTool.js`）就 `CTX.gamePaused = true`，
   记住进入前的暂停状态，退出时恢复成进入前的状态（不是无脑续玩）。
2. **架构定稿：方案 A**——同一个 `index.html`，不做第二个页面。
   第二个 index.html 需要先给 `CONFIG.customMaps` 接持久化（现在纯内存，
   刷新即丢），且会让"直接在当前战斗上现场改地形"这个能力失去意义
   （跳转页面=丢失当前对局的实时状态）。方案 A 没有这些代价。
3. **两个编辑入口要不要合并成一个**：**用户已追加拍板——不应该分开**。
   2D 缩略图（弹窗 `MapEditorDialog.js` 那套）应该是对"直接在画布上编辑"
   （`MapEditorBoardTool.js`）的**补充**，不是并列的第二套系统。具体形态
   待第二节展开实现时定（大方向：以画布编辑为主，缩略图承担"全局视角
   + 快速跳转/框选"的辅助角色）。此前"先不合并"的保守处理作废，
   合并方案在做第二节时一并设计。
4. **移动塔改成自由移动**：`MapEditorBoardTool._dragTo()` 和
   `MapEditorDialog.dragBuildingTo()` 都在调 `snapBuildingPos()`——
   只要塔有 `laneId` 就被强制吸附到那条路的折线上。改成只做世界边界
   夹紧（跟水晶枢纽这类没有 `laneId` 的建筑现在的"自由摆放"一致），
   摆错位置交给已有的结构校验红线去提示，不再由拖拽本身强制拦。

## 二、弹窗编辑器：窗口放大 + 加塔/编塔（已拍板）

1. **窗口放大**：`.modal-box` 全局上限是 `max-width:620px`，
   `MapEditorDialog.js` 的画布尺寸 `CANVAS_DISPLAY_PX=380` 就是为了
   塞进这个上限选的。给地图编辑器单独开一档更大的弹窗尺寸样式。
2. **加塔**："建筑摆放"模式现在只能拖已有的 `draftBuildings`，没有
   "点空地新增一座塔"——复用主画面工具条 `_addTowerAt` 那套"就近吸附到
   最近的路"逻辑。
3. **编塔属性**：现在选中一座草稿塔只能改档位（`STRUCT_TIERS` 下拉），
   改不了武器/技能/召唤水晶这些——复用现有的 `AttributeEditor`
   （选中草稿塔时弹出编辑面板），不新造一套编辑 UI。
4. **两个入口合并（用户追加拍板）**：2D 缩略图是画布编辑的补充，不是
   独立系统——具体形态：以 `MapEditorBoardTool.js` 的画布编辑为主视图，
   `MapEditorDialog.js` 那套缩略图/弹窗形态收编成主视图旁边的一块
   辅助面板（全局视角+跳转），而不是各自独立打开、独立暂停恢复的两个
   入口。
5. **新建塔的塔选择器（用户追加拍板）**：缩略图/画布旁新增一个"塔选择器"
   面板，覆盖三种新增方式：
   - 从零新建（走默认属性起步，跟现在 `_addTowerAt` 的默认值逻辑一致）；
   - 套用已有某座塔的属性（"格式刷"——选中一座参照塔，新塔直接复制它的
     武器/技能/属性，位置仍按点击处/就近吸附算）；
   - 存成模板、以后新增时直接套用模板（模板是"属性集合"的具名存档，
     不与某一座具体的塔绑定，可以反复套用到多座新塔上）。
   这一条把"加塔"从"造一座默认塔"扩成"造一座任意塔"，模板存储用什么
   载体（内存/localStorage）留到实现这一节时定，不在这里预先拍板。

## 五、小兵寻路：从"精确路点"改成"前瞻插值点"（已拍板，方案 A）

`LaneMovementSystem._advanceAlongLane` 现在的转向目标是路点数组里的
**精确坐标**（`target = wps[idx]`），导致整波小兵在拐弯处会向同一个
像素点收敛，形成"漏斗"观感。改成 pure-pursuit 打法：转向目标从
"折线上前瞻一段弧长的插值点"算，拐弯天然被削成弧线。`_laneWaypointIndex`/
弧长这些下游一堆系统在用的记账逻辑（出兵间距、集火优先级、走廊排队力、
"外塔各在自己半区"校验）不用动，只改"往哪个方向使劲"这一步的算法。
方案 B（纯流场驱动，改动大风险高）明确不做。

## 六、多阵营架构 + 中立野怪泛化（最大的一块，需要先写设计报告）

### 需求原文
- 地图编辑器要能**增/减阵营**（不只是蓝红两个）。
- **阵营淘汰规则**：某阵营水晶枢纽被摧毁 → 该阵营停止出兵，且
  **攻击该阵营的路径也停止出兵**（不是整个敌对阵营停摆，只是"打向
  已淘汰阵营那条路"停）。
- 以后要支持**中立野怪阵营泛化**（巨龙只是其中一种）：出生地、
  出生路径、出生条件都要能在地图编辑器里配。
- 整体调性："丰富的玩法，乱七八糟打来打去，看起来爽"——多阵营混战，
  路径可能汇合。

### 三个已拍板的设计决定
1. **阵营淘汰后果**：塔/建筑保留，仍可以被攻击/反击（不是变中立、
   不是消失）。
2. **增/减阵营的时机**：地图作者时间——地图声明自己支持几个阵营、
   初始建筑/路径怎么配，对局中阵营数固定，不支持中途动态加入第三方。
3. **多阵营汇合路段的战斗**：自然交战，不需要额外规则——现有的
   `canTarget`/索敌半径已经是"附近任何敌对阵营都可以打"，汇合点自然
   变成混战区，不用另加机制。

### 已勘查到的现状（好消息 + 真正的卡点）
- `FactionSystem.js` 的阵营关系表**本来就是通用的**（`ENEMY_PAIRS` 是
  任意对集合，`declareEnemies()` 函数已经留好，一直没人调）——这层
  不用改。
- `MapSystem.js` 摧毁水晶枢纽时已经发 `map:mainNexusDestroyed` 事件
  （现在没人监听），`CTX.__towerRules.waveOn` 已经是按阵营独立的开关——
  "某阵营停止出兵"这半件事管道是现成的。
- **真正的卡点**：`LaneWaveSystem._enqueueForFaction` 第112行
  `const enemy = faction === FACTIONS.BLUE ? FACTIONS.RED : FACTIONS.BLUE;`——
  "这条路打谁"是代码里现算的"另外那一个"，不是地图数据里存的。多阵营/
  路径汇合要求路径数据本身能表达"这条路归属哪个阵营、打哪个阵营"，
  这是整个多阵营改造的地基。
- 全仓库搜了一遍，**27 个文件**在某种形式上写死了"正好两个阵营"
  （对称校验、配色表两值、基地圈两角点、出兵广播、龙魂加成分配……），
  分布在数据/系统/表现/UI 四层。规模上不小于这次做完的地图编辑器项目，
  加上中立野怪泛化只会更大。

### 执行方式
不直接改代码——先写一份设计报告（比照当初地图编辑器那份的规格）：
逐个过一遍这 27 个文件，分成"天生支持 N 阵营不用动"和"写死两阵营
要改成读数据"，给出阵营数据模型（地图声明支持哪些阵营、每条路归属/
目标阵营）、淘汰→停止出兵的完整链路、中立野怪泛化方案，最后给分阶段
实施顺序。这一块预计跨度最大，今晚未必能做完，前面五块做完之后再开始，
做多少算多少，每个阶段单独测试+提交。
