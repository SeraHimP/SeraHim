# Q4　渲染与性能重构设计文档 + 三周执行排期

> 状态：第 1-10 节是原始方案（未动渲染代码）；第 11 节是用户后续追加的"接下来三周做显示效果重构，先写规划"这个要求的落地排期，已按"报告范围你自己权衡"的授权直接写成可执行计划，自查过没有问题即视为可以开工，不再二次等待确认。
> 范围：只覆盖"显示效果太差劲、不像 2026 年的游戏"这一条（Q4）。Q2（阵营/龙魂平衡）在另一条线里跑 `balance_matrix`，与这份文档无关。

---

## 0. 结论先行

**诊断**：不是引擎/管线不行，是**零美术资产**。

逐条核实过现有渲染代码（不是猜测，见第 1 节的文件/行号出处）后发现一个反直觉的事实：这个项目的**渲染管线本身已经相当讲究**——ACES 电影级色调映射、Bloom 辉光、FXAA、跟随视野的动态阴影、半球光昼夜系统、天气可视化、法线贴图水面、实例化植被、甚至试做了真 HDR 输出探测。这些是很多同量级项目都懒得做的东西。

但**所有单位和建筑的模型，从一开始到现在，都是纯几何拼接 + 顶点纯色**——没有 UV、没有贴图、没有法线贴图、没有粗糙度/金属度贴图，材质是最基础的 Lambert（塔）/BasicMaterial（小兵，见 `UnitLayer.js:195`）。GLTFLoader 之前接过 GLB 模型，但用户当场判定"现有的模型很烂"，整条路被禁用（`UnitMeshFactory.js:17` 注释）——问题出在**当时的模型资产本身太糙**，不是 GLB 这条技术路线错了。

也就是说：打了一手好光，照的是一堆没上色的白模。这才是"完全看不出来是 2026 年的游戏"的真正原因，不是帧率、不是分辨率、也不是缺后处理。

**推荐路线**：不推倒渲染管线，改为「材质/资产层大改 + 管线针对性补强 + 性能预算体系」三线并行，每一段都能独立验收、独立上线，不是一次性大爆炸式重写。

**构建工具链**：保留现在"改代码、刷新浏览器就看到"的开发体验，不引入打包器/npm 依赖。只新增一条**离线资产处理脚本**（纯 Node，不进浏览器运行时，跑一次生成/压缩贴图落盘），运行时代码逻辑不变。详见第 6 节。

**移动端**：输入层（Pointer Events 统一鼠标/触屏、已支持捏合缩放）和视口 meta/PWA manifest 都已经就绪，缺的是**性能自适应**（分辨率动态缩放、影子/后处理分档、LOD）和真机验证，工作量比想象中小很多。

## 1. 现状审计（有出处，不是印象）

### 1.1 渲染管线层——已经不错的部分

| 能力 | 现状 | 出处 |
|---|---|---|
| 色调映射 | ACES Filmic，默认开启 | `ThreeRenderer.js:102` |
| 后处理 | EffectComposer：RenderPass → Bloom → FXAA → OutputPass，四段管线都在 | `ThreeRenderer.js:392-409` |
| 阴影 | 平行光 + PCFSoftShadowMap，阴影相机**跟随视野**而不是罩全图（分辨率利用率高），分"全部/仅静态/关闭"三档 | `ThreeRenderer.js:334-376` |
| 光照 | 半球光（天空色/地色）+ 平行光，按物理辐照度标定（`IRRADIANCE_TARGET = π`），不是拍脑袋的强度值 | `ThreeRenderer.js:39-53` |
| 昼夜 | 完整的相位系统 + 光照/雾/天空同步变色 | `DayNight.js` |
| 天气 | 雨/雪/雾/风粒子可视化独立层 | `WeatherLayer.js` |
| 水面 | 法线贴图 + 滚动 UV + Lambert | `WaterLayer.js:101-103` |
| 植被 | InstancedMesh，几百棵树/岩零开销 | `VegetationLayer.js:5,77` |
| HDR 输出 | 有完整的能力探测+真机自适应，SDR 屏自动关闭不致命降级 | `ThreeRenderer.js:419-569` |
| 光源池 | 塔灯/火炬用固定大小的池子（避免动态灯光数导致的着色器重编译卡顿） | `ThreeRenderer.js:285-317` |

这一层的工程质量是可以直接拿来当地基用的，**不建议推倒重来**。

### 1.2 资产/材质层——真正的缺口

| 缺什么 | 证据 |
|---|---|
| 单位无 UV | `UnitMeshFactory.js` 的 `mergeParts()`（27-55行）只写了 position/normal/color 三个 attribute，从未生成 uv |
| 单位无贴图 | 全项目搜索 `MeshStandardMaterial`/`normalMap` 等只命中水面、崖壁、（一处未查具体用途的 `MeshStandardMaterial` 在 UnitMeshFactory.js:1248，需要在方案落地前确认是不是水晶自发光材质的孤例） |
| 单位材质是最基础档 | 塔/小兵：`MeshLambertMaterial`（无镜面高光、无粗糙度层次）；小兵血条/部分特效用 `MeshBasicMaterial`（完全不受光） |
| 无骨骼动画 | 全项目搜 `SkinnedMesh`/`AnimationMixer`/`bones` 零命中——单位是刚体网格 |
| 无逐帧姿态动画 | `UnitLayer.js` 里对单位网格的操作只有：朝向旋转（873/883行）、按属性整体缩放（774行）、水晶自转（784/802行）——没有走路摆动、没有攻击前摇/后摇、没有受击反馈动画 |
| 无实例化合批 | 塔与小兵各自独立 Mesh（几何/材质按 key 共享，但 drawcall 不共享）——44 塔 + 100~200 小兵同屏时是等量的独立 drawcall |
| 无 LOD | 远处的塔/小兵与近处用同一套几何精度 |

### 1.3 输入/移动端层——比想象中现成

| 项目 | 现状 |
|---|---|
| 视口 meta | 已配置 `width=device-width`，禁用双指缩放页面（避免与游戏内缩放冲突） |
| PWA | 已有 `manifest.json` + `mobile-web-app-capable` |
| 触屏输入 | `CanvasController.js` 用的是 **Pointer Events**（`pointerdown/pointermove`，102/128行），天然统一鼠标/触屏/触笔，已支持捏合缩放（5 个缩放入口之一） |
| 缺什么 | 没有按设备性能自动降档的机制；没有做过真机（尤其中低端安卓）性能验证 |

## 2. 为什么"看起来不像 2026 年的游戏"——收敛判断

把光照/阴影/后处理这些"管线"效果单独拎出来看，其实已经是同类网页小游戏里偏上的水准。真正拉低观感的是三件事的叠加，按影响力排序：

1. **材质**：低多边形风格如果想好看，靠的从来不是几何精细度，而是材质质感——AO 阴影窝、边缘磨损、渐变高光。现在是纯顶点色平涂，任何角度看都是一片死板的塑料感。
2. **动画**：完全静止的单位（除了整体位移和朝向）在视觉心理上直接被归类为"没做完的原型"，不管灯光多讲究。
3. **轮廓/风格化收尾缺失**：没有描边、没有 AO、没有任何"让低多边形看起来是故意的、不是懒得建模的"视觉语言——对比 Monument Valley、Overcooked、甚至很多 itch.io 独立塔防的截图，这条差得最明显。

分辨率、帧率、抗锯齿这些"性能观感"层面反而不是主要矛盾——现有的 FXAA + DPR 适配已经在及格线以上。

## 3. 目标与非目标

**目标**
- 视觉水准提升到"同类策略/塔防类网页游戏的商业发布水准"（参考系：itch.io/Steam 上排名靠前的 2.5D 策略游戏，而不是 3A 写实大作——这决定了美术方向，见第 4 节）。
- 桌面 + 移动双端都要跑起来，移动端允许自动降档但不允许直接跑不动。
- **逻辑层零改动**——这本来就是这份代码一直坚持的纪律（`ThreeRenderer.js` 开头写着"本文件只读实体/地图数据，不写任何实体字段"），渲染重构不应该也不需要碰任何 `src/core/`、`src/systems/`、`src/data/` 下的东西。这是这次重构风险可控的根本原因：改的是"怎么画"，不是"怎么算"。

**非目标（这次不做）**
- 不改变任何游戏规则、数值、平衡（那是 Q2 的事）。
- 不做服务器渲染/原生客户端。
- 不必然升级 Three.js 版本——r169 已经是相对新的版本，除非评估中发现某个具体能力缺失（例如更完善的 Node-based 材质系统），否则不为了"升级"而升级。
- 不引入完整的骨骼动画/DCC 建模流程作为**第一步**——这是成本最高的路径，留到确认前几阶段效果后再决定要不要投入（见第 4 节候选 B）。

## 4. 技术路线：三个候选与推荐

### 候选 A：贴图流 PBR 化（保守）
给现有程序化几何做 UV 展开，套 `MeshStandardMaterial`，配手绘或 AI 生成的贴图（基础色/法线/AO/粗糙度）。风格保持"低多边形写实"，质感直接跃升一个档次。
- 工作量：中。风险：低（材质系统改动局限在 `UnitMeshFactory.js`，不动其余管线）。
- 缺点：仍然依赖"有人画贴图"，如果没有稳定的贴图产出渠道（人工或 AI 管线），这条路会卡住。

### 候选 B：正式建模流程重启（重度）
用 Blender 等工具做真模型（可以上 AI 建模/贴图生成工具辅助），走 `GLTFLoader`（已经 vendored 好，接口都在，只是被禁用）。之前失败的教训是"模型资产本身很烂"，不是 GLB 这条通路本身有问题。
- 工作量：最大，且高度依赖美术资产的产出质量和产出速度，是这三条里唯一"经验证会失败一次"的路线（除非这次能保证资产质量）。
- 优点：上限最高，能做到最接近"正经游戏"的观感。

### 候选 C：风格化程序化升级（折中，推荐主线）
保留纯程序化生成（不依赖外部美术资源、不依赖建模师/AI 建模稳定产出），但把材质和后处理都升级到"程序化 PBR + 风格化收尾"：
- 给合并几何加 UV 展开，用 Canvas 2D **离线生成**细节贴图（噪声、渐变、描边遮罩、AO 烘焙进纹理图集），换成 `MeshStandardMaterial`。
- 加轮廓描边 Pass（成本低、风格化收益极高，很多独立游戏靠这一条就把"廉价感"扭转过来）。
- 加 SSAO（低多边形场景对 AO 极其敏感，缝隙/接缝处一旦有柔和暗角，立刻显得"有实体感"）。
- 补上第 2 节提到的动画缺口：简单的程序化动画（走路摆动、攻击前摇/后摇的整体形变或缩放脉冲、受击闪白/后仰）——不需要骨骼，纯 Tween 就能做出"活起来"的效果，性价比全文最高的一项。

**推荐 C 为主线，为 A 预留升级路径**：把材质系统设计成"纹理槽位化"——程序生成的贴图和未来手绘/AI 生成的贴图走同一套材质接口，先用程序生成的占位，效果验证后随时可以整批替换成更精细的贴图而不用重构材质系统。这样即使以后想往 A 或 B 走，这一步也不是弯路。

**推荐理由**：
1. 零外部依赖，工期和质量完全在工程可控范围内，不会像 B 那样被"美术资产迟迟出不来/出来了还是烂"卡住第二次。
2. 这个项目的规则还在高频迭代（这条分支这几周的提交历史看得很清楚），美术资产投入得越精细，规则一改就返工成本越高——程序化生成天然对"某个兵种改名/换定位"免疫。
3. C 方案里的每一项（描边、SSAO、动画、贴图）都可以独立做独立验收，不需要等一个大方案全部完工才能看到进展，符合"分阶段"的诉求。

## 5. 具体技术清单（每项独立可验收）

| # | 项目 | 说明 | 预估收益/成本比 |
|---|---|---|---|
| 1 | 程序化动画（走路/攻击/受击） | 纯 Tween，不需要骨骼；`UnitLayer.js` 已有的每帧更新循环里加姿态插值 | 全清单最高 |
| 2 | 轮廓描边 Pass | 后处理管线里加一个基于法线/深度边缘检测的 ShaderPass | 高 |
| 3 | SSAO | vendored 一份（或参照现有 Bloom 的手法自己写一份精简版），接进现有 EffectComposer | 高 |
| 4 | UV 展开 + 程序生成贴图 | `UnitMeshFactory.js` 的 `mergeParts` 需要重写以携带 UV；贴图用 Canvas 2D 离线烘焙（噪声/渐变/AO） | 中高 |
| 5 | 材质升级到 Standard/Physical | 配合第 4 项一起做，否则贴图槽位没处挂 | 与第4项绑定 |
| 6 | 塔/小兵实例化合批 | 同类型（同阵营同层级/同兵种）units 改 `InstancedMesh`，逐实例传颜色/朝向/缩放 | 性能向，中 |
| 7 | 远处 LOD/简化 | 视野外或远处单位用更粗糙的几何或直接 impostor（billboard） | 性能向，中，收益视同屏单位数而定 |
| 8 | 移动端分辨率自适应 | 按帧时间动态调 `setPixelRatio`，而不是固定用 `devicePixelRatio` | 移动端必需 |
| 9 | 画质分档预设 | 低/中/高/自动——影子档位已经有三档（`setShadowLevel`），把 Bloom/SSAO/描边/分辨率一起纳入统一档位系统 | 移动端必需 |
| 10 | 真机验证 | 至少一台中端安卓 + 一台 iOS，量出实际帧率再定默认档位 | 必须做，不能只凭估算 |

## 6. 构建工具链决策

你已经明确"放开约束，怎么做更好你权衡"。工程判断如下：

**不引入打包器/npm 运行时依赖**，理由：
- 这个项目现在的开发体验（改代码、刷新浏览器、立刻看到效果）是明确的资产——`docs/DEVELOPMENT.md` 全篇的调试心法都建立在"能直接改能直接跑"上，引入打包器后每次改动都要多等一次构建，且构建工具本身的配置、依赖版本漂移会变成新的维护负担。
- 第 5 节清单里的改动**不需要**打包器就能做——UV 展开是几何计算（纯 JS）、贴图生成用 Canvas 2D API（浏览器原生）、SSAO/描边是 Shader（Three.js 原生支持自定义 ShaderPass）。真正可能用得上"构建期工具"的只有"贴图压缩"这一类离线优化，而这类工作**不需要**在浏览器运行时里做。

**新增一条边界清晰的东西**：`tools/bake-assets.mjs`（比照现有 `tools/balance_matrix.mjs` 的定位——纯 Node 脚本，不是构建步骤，不参与游戏运行时）：
- 职责：离线生成/压缩程序化贴图图集，落盘到 `assets/generated/` 之类的目录，运行时直接 `<img>`/`fetch` 加载，和现在加载 `assets/textures/*.png` 完全一样的路径。
- 好处：贴图生成逻辑只需要跑一次（除非改了生成算法），不占运行时开销；同时保留"贴图生成算法本身也是可读的 JS 源码，可以调、可以复现"的透明度。
- 这不是"引入构建步骤"——`index.html` 依然可以直接打开就跑，`bake-assets.mjs` 只是一个类似"重新生成地图缩略图"性质的离线工具，不跑它也不影响游戏运行（用已经生成好、提交进仓库的贴图文件）。

如果第 5 节清单执行到"候选 A/B"阶段（引入手绘或 AI 生成的高精度贴图/模型），到时候可能需要贴图压缩（KTX2/Basis）之类的工具链——那一步再评估是否值得为了压缩率引入构建步骤，不在这次的范围内提前决定。

## 7. 性能预算与验收标准（草案，需要真机数据验证后调整）

- **桌面**：1080p、满配对局（44 塔 + 峰值约 150~200 小兵同屏）稳定 60fps，高画质档（全影子+全后处理）。
- **移动·中端**（比照 2~3 年前的中端安卓/iPhone）：自动档下 30fps 起，允许自动降到"关闭阴影+关闭SSAO+分辨率缩放到 0.75x"这一档。
- **移动·低端**：允许进一步降档（关闭描边、关闭 Bloom、分辨率 0.5x），只保证"能玩，不保证好看"。
- 验收方式：不能只凭理论估算——需要在真机上跑，用 `performance.now()` 打点或直接用浏览器 devtools 的 FPS 计量，量出来再定档位阈值。

## 8. 分阶段实施计划

每个阶段都应该能独立提交、独立跑 `node tests/run_all.mjs`（渲染层这次没有 sim 测试覆盖，但改动不该影响任何逻辑层测试——如果哪个阶段的改动导致 sim 测试变化，说明改动越界了，需要立刻停下核查）。

- **P0　基础设施**：`UnitMeshFactory.js` 的 `mergeParts` 加 UV 支持；材质从 Lambert 换成 Standard（先不挂任何新贴图，验证换材质本身不会让画面变化——类似当年"光照基座"那一步"验收标准是画面不变"的做法）。
- **P1　动画**：走路摆动 + 攻击前摇/后摇 + 受击反馈。全程不需要 P0 完成即可独立开始（不依赖材质），可以并行甚至提前做，性价比最高、见效最快。
- **P2　材质与光影质感**：程序生成贴图（噪声/AO/渐变）+ 轮廓描边 + SSAO。
- **P3　性能**：实例化合批 + LOD + 分辨率自适应 + 画质分档系统。
- **P4　移动端专项**：真机测试、按 P3 的分档系统定阈值。
- **P5（可选，视 P0-P4 效果和资源决定要不要走）**：候选 A（手绘/AI 贴图替换程序生成贴图）或候选 B（正式建模）。

建议顺序：P1 先做（最快看到"活起来"的效果，且完全独立、零风险）；P0→P2 次之；P3→P4 在前两阶段效果确认后再排期，因为"值不值得做实例化"取决于 P2 做完之后实际的 drawcall/性能画像，现在测的性能数据可能会因为材质改动而变化。

## 9. 风险与回滚

- 每一阶段的改动都建议保留旧路径的开关（参照现有代码风格——`setBloom`/`setFXAA`/`setShadowLevel` 这类每项都能独立开关的先例），改坏了能立刻切回旧材质/旧几何，不需要回退代码。

### 测试怎么盯

第 8 节已经说明：渲染层没有、也不该有 `sim_*.mjs`（Three.js/WebGL 场景图不在这份仓库的 headless Node 测试框架覆盖范围内，这是既有约定，不是这次绕过 CLAUDE.md 的第 1 条硬约束）。三周里每一步的安全网是：
1. **`node tests/run_all.mjs` 必须逐步保持 0 失败**——这套回归测的是 `src/core`/`src/systems`/`src/data`，渲染层改动不该碰这些文件；一旦哪次改动导致某个 sim 用例变了，说明这次改动越界进了逻辑层，必须立刻停下来查，而不是改测试去迁就。
2. 每个可独立验收的子项做完都要**过一遍浏览器**（起 dev server，实际点开局面看效果——参照"UI/前端改动要在浏览器里过一遍"的既有要求，渲染这块比一般 UI 改动更需要肉眼验收，数值测试测不出"好不好看"）。

### Week 1（P1：程序化动画——见效最快、零风险，独立于材质/贴图，可以立刻开始）

- **Day 1**：在 `UnitLayer.js` 现有的逐帧同步循环里加一份纯渲染层的姿态状态（走路相位、攻击前摇/后摇计时、受击闪光计时），全部挂在 `en`（渲染层自己的 per-entity 缓存对象）上，不写任何 `entity` 字段——延续 `ThreeRenderer.js` 头注"只读实体/地图数据"的既有边界。这一天先把状态管线搭起来、默认关闭效果，验收标准是**画面不变**（与第 8 节 P0 那条"先验证换材质本身不引入变化"同一个做法，先立好"这一步没有副作用"的锚点）。
- **Day 2-3**：走路摆动——纯 Tween（正弦波驱动的躯干起伏 + 四肢/部件的小幅摆动，用现有合并几何的分组做整体形变，不需要新几何）。小兵先做，覆盖 melee/ranged/siege/super/totem 等现有兵种模型。
- **Day 3-4**：攻击前摇/后摇——攻击触发时（复用 CombatSystem 已有的攻击事件/时序，渲染层只读不写）做整体缩放脉冲或朝目标方向的短促前倾，塔和小兵都要有（塔的攻击动作可以更克制，毕竟塔身不动）。
- **Day 4-5**：受击反馈——挨打瞬间的短暂闪白 tint + 轻微后仰/抖动，复用现有的伤害数字/受击可视化事件源，不新开一条事件通道。
- **Week 1 收尾**：过一遍浏览器实际对局观察四类动画是否自然（不生硬、不穿模）；`node tests/run_all.mjs` confirm 0 失败；P1 单独提交（第 9 节的"每阶段独立提交、独立可回滚"）。

### Week 2（P0 + P2：材质与光影质感——本三周风险最高的一段，视觉提升最大的一段）

- **Day 6**：P0 基础设施——重写 `UnitMeshFactory.js` 的 `mergeParts()`，让合并几何在 position/normal/color 之外再吐出一份 UV；材质从 `MeshLambertMaterial`/`MeshBasicMaterial` 换成 `MeshStandardMaterial`，先不挂任何新贴图。验收标准仍是"画面基本不变"（换皮不换效果），确认这一步本身不引入回归后再往下叠贴图。
- **Day 7-8**：`tools/bake-assets.mjs`——离线 Canvas 2D 生成噪声/渐变/AO 贴图图集，落盘到 `assets/generated/`，运行时按现有 `assets/textures/*.png` 同款路径加载（第 6 节已经定过这条不算引入构建步骤）。风格参数按上面"#2"的默认值起步。
