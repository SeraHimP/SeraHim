# 窗口设计规范

用户定稿：**模板编辑器就是标准**，其余窗口逐步向它靠。
这份文件是那个标准的成文版 + 待改造清单。改窗口之前先读一遍。

参考实现：`src/ui/AttributeEditor.js` 的 `_renderTemplateEditor`
（左树 + 右表单 + 页面注册表），样式在 `index.html` 的 `.tpl-*` 一段。

---

## 一、骨架：左树 + 右表单

```
┌────────────────────────────────────────────┐
│ 📐 标题                                     │
├──────────┬─────────────────────────────────┤
│ 分组标题  │ 面包屑：当前对象 · 当前页 [⚡角标] │
│  ▸ 节点   ├─────────────────────────────────┤
│  ▾ 节点   │ 页签（单页时不画）                │
│    子节点 │ 作用域条（只在该页真读它时才画）    │
│    子节点 │ 说明行（只描述该页真读的维度）      │
│ 分组标题  │                                 │
│  节点     │ 表单内容                         │
├──────────┴─────────────────────────────────┤
│ 💾 保存 📂 打开 📋 JSON   [应用][确定][取消] │
└────────────────────────────────────────────┘
```

硬要求：

1. **纵向导航承担"我在哪"**。改版前是三层横排页签，一屏能出现四行胶囊按钮，
   而"当前在编辑谁"要横着读三行才拼得出来。
2. **非当前分组折叠**。全展开会超出可视高度，把后面的分组挤到折叠线以下 ——
   看不见的入口等于不存在。
3. **面包屑写"对象 · 页"**，右侧再放即时生效角标。

## 二、控件不许撒谎（本项目最贵的一条）

> 控件摆在那儿却不起作用，比没有这个控件糟得多 —— 它让人相信了一件假事。

- **每一页自己声明它读哪些维度**，界面由声明推导，不在渲染里写第二份 `if`。
  参考 `AttributeEditor._TPL_PAGES` 的 `{ faction, apply, action, writes }`。
- 反例（真实发生过）：改版前每一页都画【阵营】【应用范围】两条作用域条，
  而真读它们的只有四页。在"建筑体积"页把阵营切到 🔴仅红方 再改尺寸，
  改的是双方共享的 `CONFIG.buildingSizes`，面板却写着"仅红方"。
- **说明行只描述该页真读的维度**；不读的维度要明写"本页对双方共同生效"，
  而不是默认显示一个会误导的值。
- **提交按钮印出写入目标**（"应用 → 外塔·属性数值" / "应用 → 全局·建筑体积"），
  用户不该靠猜。
- **即时生效的控件要有角标**（⚡），与"改完要点应用"的控件在视觉上分开。

## 三、页脚：应用 / 确定 / 取消

实现见 `src/ui/dialogFooter.js`。语义必须三者互不重叠：

| 按钮 | 作用 |
|---|---|
| 应用 | 提交改动，**窗口不关**。提交后基线前移（之后"取消"回到这一刻） |
| 确定 | 提交 + 关闭 |
| 取消 | 丢弃**自上次提交以来**的改动 + 关闭 |

- **"取消"必须真的能回滚。** 本项目的画质开关是即时预览的（阴影/泛光/水面点一下
  就看到效果），那是它们的价值，不该改成"点了没反应"。所以取消要靠快照回滚 ——
  否则点开设置、乱翻一通、点取消，改动全留着，那个按钮就是个谎。
- **快照要覆盖该窗口会动的全部状态。** 漏一个 = 那一项取消不掉，比没有取消更糟。
  渲染器实例上的开关（`window.__three.*`）不在 CONFIG 里，回滚后要重新推一次，
  否则配置对了、画面还停在被取消掉的状态上 —— 最难查的那种不一致。
- **基线前移**：点过"应用"再点"取消"，回到的是应用那一刻，不是打开那一刻。
  不前移的话，"应用 → 再改坏 → 取消"会把已经确认过的那批一起吞掉。

### 什么窗口**不该**套三按钮

判据只有一条：**这个窗口有没有"改了但还没生效"的中间态。**

| 窗口 | 页脚 | 理由 |
|---|---|---|
| 设置 | 应用 / 确定 / 取消 | 有中间态，且开关即时预览 → 取消必须回滚 |
| 模板编辑器 | 保存/打开/JSON + 应用 + 关闭 | 应用按页写入，已符合语义 |
| 模式与地图 | 确定 / 取消 | 切模式会**立刻重建整张地图**，没有中间态；回滚等于再重建一次，不是点取消想要的 |
| 添加单位 | 建造 / 加入清单 + 取消 | 这是**动作**窗不是设置窗，"应用"无意义 |
| 详情（只读） | 关闭 | 没有可提交的东西 |

硬套只会造出没作用的按钮 —— 那正是第二节要消灭的东西。

## 四、别解释机制怎么跑（用户定稿，铁律）

用户原话："所有UI中除了对技能/状态/兵/等的必要介绍外，删除所有告诉'我'这套机制怎么运行等的废话。"

- **允许**：技能/状态/兵种/塔/天气等**游戏内容本身**的说明——玩家需要知道"这个东西是什么、干什么用"。
- **不允许**：解释**编辑器/系统内部怎么实现**的文字——那是写给自己看的设计笔记，不是给用户看的界面文案。
  典型违规句式："这里用了 XXX 算法/数据结构"「拖动期间只画屏幕反馈，松手才真正生效」这类"我是怎么做的"说明，
  用户不需要知道机制，只需要知道"能做什么、怎么操作"。
- 判断法：把这句话删掉，用户会不会因此不知道**怎么操作**？不会的话就是废话，删。
  会的话尽量压成操作提示本身（"拖动移动/点击插入"），别带着"为什么这么设计"的解释。
- 这条本身也适用于**这次地图编辑器新写的那批 UI**（区域参数表单/折线造墙/路径编辑的提示文字，
  写的时候顺手把设计动机也讲给用户看了，本条铁律定稿之后需要按这条标准清一遍——见任务清单）。
- 本条不追溯审查代码注释/提交信息——那些是写给协作者看的，跟本条管的"界面上给用户看的文案"不是一回事。
