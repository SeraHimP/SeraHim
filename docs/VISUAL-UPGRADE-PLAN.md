## 1. 本轮新发现：轮廓描边的具体 bug 清单

用户实机报告：开启描边后，**雨变成了黑色粗线条**。已经查过根因和影响范围（**还
没动代码，只是诊断**）：

### 根因

`NormalDepthPrepass`（`src/presentation/PostFX.js`）用 `scene.overrideMaterial`
把整个场景重渲一遍，产出法线/深度贴图，供描边的 Sobel 边缘检测和 SSAO 共用。这个
"整场景重渲"没有排除掉"非实体几何"的 FX/粒子类对象——线段（`LineSegments`）、
点精灵（`Points`）这类东西套上 `MeshNormalMaterial` 后法线编码是垃圾值，加上它们
天然是"极细的东西衬着大片空白背景"，Sobel 边缘检测会把它们的轮廓放大成粗黑线，或
者在背景空白区域炸出成片噪点（这与本项目更早诊断出的"描边背景噪点"是同一个根因，
不是两个独立问题）。

### 这不是新坑，是已知修复模式的漏网之鱼

塔的血条/护盾图标（`Sprite`）之前踩过同一类坑（v51.33，任务 #104——SSAO 把血条
形状算成一圈错误阴影）。当时的修法是给这类"永远画在最上层、不该参与场景遮蔽/边缘
判定"的对象一个专用 `HUD_SPRITE_LAYER`，`NormalDepthPrepass` 预渲染时相机临时关掉
这个 layer，主渲染（beauty pass）不受影响照常显示。这个技术方案本身是对的，只是
没有推广到其它同类对象——当时只顾着修血条，没有意识到"线/点类 FX 几何"是同一个
问题形状。

### 已确认命中同一根因的对象（都不在 `HUD_SPRITE_LAYER` 里，且都是"线/点"类几何）

| 对象 | 文件 | Three.js 类型 | 症状 |
|---|---|---|---|
| 雨 | `WeatherLayer.js:80` | `LineSegments` | 用户实机报告：变成黑色粗线条 |
| 雪 | `WeatherLayer.js:95` | `Points` | 大概率同类噪点，尚未逐一实机验证 |
| 尘埃（`_dust`） | `WeatherLayer.js` | `Points` | 同上，尚未逐一实机验证 |
| 水晶/枢纽装饰粒子壳 | `UnitMeshFactory.js:1353` | `Points` | 同上，尚未逐一实机验证 |

这四个大概率是同一根因、同一种修法：把它们纳入现有的 `HUD_SPRITE_LAYER`（或者
新开一个语义更准确的 `FX_PARTICLE_LAYER`——两者对预渲染相机的处理逻辑完全一样，
只是要不要区分"贴屏 HUD"和"世界空间粒子"这两个概念，动手时再定）。

### 还没查、动手阶段要过一遍的

投射物（`ProjectileSystem` 对应的渲染层）、技能特效（`EffectsLayer.js` 里的
`Batch`，目前只确认它用了 `CanvasTexture`，具体是不是 `Sprite`/`Points` 家族没
查完）、伤害飘字，如果也是 `Sprite`/`Points`/`LineSegments` 家族，大概率是同一
个坑。动手时应该用同一份检查清单（`grep "new THREE.LineSegments\|new THREE.Points\|new THREE.Sprite" src/presentation/*.js`，
逐个核对是否已在 `HUD_SPRITE_LAYER`）一次性扫描修完，不要修一个漏一个。

## 2. 优先级路线图

综合我们自己的判断和 ChatGPT 上一轮回复（已核对过其判断依据，没有照单全收），
排成四层：

```
P0  塔/兵轮廓重做          Outline 描边 bug 修复
P1  场景小型道具库          场景密度分区          色彩体系
P2  渐变式地形高低差        塔夜间光照重做
P3  更多环境模板/天气表现/特殊地形/UI 美术打磨
```

**为什么 Outline 修复和塔/兵轮廓重做都是 P0**：现在最大的画面缺陷是"东西长什么
样还没解决"——描边是这条风格化路线里"让低多边形看起来是故意的、不是没做完"的
核心视觉语言，一天不修就有一天视觉上"看着像半成品"；塔/兵模型不重做，后面所有
场景/光照工作做的都是给旧模型化妆，性价比低。

**为什么高低差和光照排 P2 不是 P0**：这两项是"锦上添花的构图/氛围工具"，不是
"地基"——先把轮廓/描边这些地基级问题解决，场景多样性和色彩体系跟上，再谈空间
层次和氛围光照，效果才叠得上去。但也不能拖到最后：高低差不只是装饰，是构图工具
（能把"平面路线图"变成"有空间层次的战场"），塔光照现在判定为"物理正确 vs 卡通
美术拧巴"，拖太久会让新模型（P0 做完）用旧光照方式呈现，白瞎了新模型的轮廓设计。

## 3. 各条目详细说明

### 3.1 P0-A：Outline 描边 bug 修复

见第 1 节。目标：描边重新启用后，天空/背景空白区域没有噪点，雨/雪等粒子类 FX
不再被描边。验收标准：Playwright 实机开启描边，截图核对背景干净、天气效果正常，
0 条真实控制台报错。

### 3.2 P0-B：塔/兵轮廓重做

> **2026-09-04 更新：本项已被用户明确挂起（"先挂起这个重做模型"）——下面这份
> 设计草案原样保留供后续参考，但当前不投入开发，不要在没有新指示的情况下启动。**
> 挂起原因未展开说明，按字面理解为"先排后面"，不是"取消"。

约束：纯程序化几何（Box/Cylinder/Cone/Icosahedron 类基础体拼接），零外部模型/
贴图，轮廓优先（不同兵种/塔档位靠外形轮廓一眼分辨，不靠细节贴图）。

验收方法（借用 ChatGPT 建议、认可有效）：每做一个单位生成 100%/50%/25% 三档
缩放截图，转灰度，25% 下仍能区分"近战/远程""普通/超级""一级/二级/三级"才算过。

**待做清单**（每类先出一版设计草图/截图核对，再落地代码）：
- 近战兵：矮胖、肩宽、下盘宽，武器/盾牌轮廓跑出身体边界。
- 远程兵：瘦高、肩窄，弓/弩轮廓横向展开、比身体更宽。
- 攻城单位：脱离人形，宽而低、底盘明显，轮子给出清晰圆形轮廓。
- 超级兵：不是"近战兵放大"，至少改变两个轮廓比例特征（头/肩/武器/身宽任选两项）。
- 塔 T1/T2/T3/枢纽：每级轮廓语言不同（矮方→高窄→大武器或宽厚底盘→顶部特殊结构/
  对称高耸核心），不是简单叠加体积。
- 敌我区分走颜色编码（己方冷色系/敌方暖色系或反过来，需与现有阵营配色核对一致），
  不与轮廓区分挤在同一套系统里——轮廓答"是什么"，颜色答"是谁"。

**已知会牵动的范围**（动手前需要先确认，不能想当然）：`UnitMeshFactory.js`（塔/
兵几何生成）、可能牵连 `VegetationLayer.js` 已经验证过的 `mergeGeometries`
索引/非索引混用坑（新模型如果混用 Cylinder 与 Icosahedron 家族，大概率会再踩
一次，动手时直接检查）、地图编辑器里"塔档位识别/自动摆放"如果读了塔的具体几何
尺寸也要核对不受影响。

### 3.3 P1：场景多样性（低成本程序化手段，团队已确认最终仍需人工审美介入）

- **小型道具库**：十几个基础模板（灌木/树桩/倒木/石堆/旗帜/路牌/篝火/木箱/花/
  蘑菇……），每类做 3~5 个变体（高宽比/旋转/顶部截面/flat face 数量微调），不
  是每种只有一个模型。
- **密度分区**：不要均匀撒——森林核心高密度、边缘中密度、道路两侧低密度、战斗区
  几乎不放，靠密度梯度本身制造"这是一片有设计的森林"而不是"一条挤出来的窄带"。
- **色彩体系**：建立 Terrain / Structure / Friendly / Enemy / Neutral / FX /
  Night 几套基础颜色关系，避免后面每加一种新对象都要重新决定配色。
- **双阵营主题化**（2026-09-04 用户新增，参考 Dota 2 天辉/夜魇分区）：地图不
  再是"中立地形 + 双色塔"这种单一基调，而是蓝方半区整体走"生机勃勃"的自然
  风格（更绿、更多植被、更明亮），红方半区整体走"熔岩地狱"风格（暗红/焦黑/
  岩浆裂纹、更少植被、更压抑的光照）。这条与上面"密度分区""色彩体系"两条不是
  互斥关系，而是同一件事的更高层级——先有"蓝热闹/红压抑"这个整体基调，密度/
  道具/配色三条具体手段再分别在两个半区各自套用不同参数。
  - 影响面：地形材质（`TerrainLayer.js`/`TerrainMaterial.js`）、植被密度与
    种类分布（`VegetationLayer.js`）、可能还有天光/雾效颜色是否要按半区插值
    过渡（避免中路出现一条生硬的"分界线"，需要设计一个过渡带）。
  - 与现有系统的关系：现在的昼夜/天气系统是**全图统一**的一套颜色状态，双阵营
    主题化是**空间上**的左右分区，两者正交、不冲突，但过渡带怎么处理（尤其是
    昼夜变化时两个半区的基调要不要一起变暗/一起下雨）需要在动手设计时想清楚。
  - 优先级：暂定跟着 P1 的密度分区/色彩体系一起做（三者关联度高，分开做容易
    互相打架），具体排期等 P0 两项做完再细化。

### 3.4 P2-A：渐变式地形高低差

技术边界（已经跟用户确认过，不用重新论证）：navgrid/寻路/索敌/弹道全部是纯 2D
判定，`heightAt(x,z)` 目前是渲染层单独查询的展示字段，仿真层不读它。渐变式高低
差（坡道爬升、之字盘山道、几级错落台地）是"同一个 (x,y) 在不同地方有不同高度"，
不违反这条 2D 假设，只需要给路点补高度值、地形网格跟着起伏、单位渲染位置跟着
高度插值——全部是渲染层工作，**禁止进入仿真坐标体系**。

### 3.5 P2-B：塔夜间光照重做

方向（已达成一致，具体分级还没最终拍板）：把"发光"和"照明"拆成两个概念——

- **发光**（负责"这里有火"）：emissive 材质 + 小型火焰/核心几何 + Bloom，不需要
  真实衰减，所有塔都有。
- **照明**（负责"这附近确实亮"）：不必每座塔都配一盏完整物理 PointLight，按塔的
  重要程度分档（例如：普通塔 0 盏、特殊塔/枢纽才配真正的动态光源），现有的
  "固定大小光源池"技术方案可以保留、复用，只是**分配策略**要从"给所有装备了武器
  的塔"收窄成"只给重要建筑"。

**待拍板**：具体分几档（现在草拟的是"关/弱/强"三档，还是就"有/无"两档）、每档
的 Bloom 强度上限（避免变成"每个单位周围一圈白光"的手游特效感）——这两条留到
真正动手改光照那一步，跟塔模型重做一起过一遍新造型再定，不提前锁死。

**是否和塔模型重做合并**：设计层面必须一起想（造型决定发光点在哪、光该从哪个
部位出来），工程层面分开做（模型改动不该牵动光照系统代码、反之亦然）。

## 4. 明确不做的事（避免范围蔓延）

- 不做真螺旋坡道（需要仿真层加高度维度）。
- 不做骨骼动画/逐帧姿态动画（一直是这条线的既定非目标，模型重做也不改变这一条）。
- 不引入外部模型/贴图资源、不引入构建工具链。
- 塔的数据结构（要不要做成 `TowerDefinition { silhouette, attachmentPoints,
  LightingProfile }` 这类统一 schema）暂不重构——ChatGPT 建议过这个方向，工程
  量比单纯换几何大得多，等 P0-B 真正动手设计出几版塔轮廓、看清楚"attachment
  point"这类抽象是否真的需要之后再决定，不提前搭一个可能用不上的框架。
