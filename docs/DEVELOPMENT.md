## 零、硬约束（违反其中任何一条，改动都算失败）

### 0.1 行尾：全仓库统一 LF、无 BOM（v43 起）

`.gitattributes` = `* text=auto eol=lf`。**改文件时不用再管行尾**，普通编辑器/脚本直接写即可。

以前这里是 `* -text`（git 不做任何转换），仓库里 CRLF+BOM / CRLF / LF+BOM / LF 四种并存，
还有 7 个文件在 CRLF 里夹着孤立 LF。每改一个文件都要先探测、再逐文件保留原样，
为此出过三次事故：

1. 往 CRLF 文件里混进几行 LF，diff 变成整段重写，真实改动被埋掉。
2. 一个测试用 `split('\n')` 切 CRLF 文件，残留的 `\r` 让 `/\/\/.*$/` 永远匹配不到整行注释
   （`.` 不匹配 `\r`，`$` 锚在字符串末尾），"检查未使用变量"的用例报了 7 个假阳性，全是注释。
3. 用 Python 改文件时 `io.open(p,'w')` 会先把文件截成 0 字节。

v43 把全仓库归一到 LF 无 BOM（`scratchpad/normalize_eol.py`，只改行尾与 BOM，
内容逐字节未变，已用"去掉行尾与 BOM 后比对"复核）。上面 1、2 两条从此不可能再发生。

**第 3 条仍然成立，与行尾无关**：任何语言里，写句柄一打开就截断文件。

```python
out = s.replace(old, new)          # 先算完
open(p, 'w', encoding='utf-8').write(out)   # 再开写句柄
```

### 0.2 交付前 `npm test` 必须全绿

```bash
node tests/run_all.mjs      # 约 6~9 分钟，41 套
```

不要用"失败集合没变"当通过标准（本项目曾长期带着 6 个失败用例，
后来查明 5 个是断言自己写错了，不是产品 bug）。**基线是 0 失败。**

新增行为**必须**配一套 `tests/sim_*.mjs` 并注册进 `tests/run_all.mjs` 的 `suites` 数组。
没有断言守着的行为，下一个人改两行就没了。

### 0.3 一切数值都必须软编码

用户原话：「所有的都不要硬编码，都应该是可编辑的软编码」。
新数值一律进 `src/data/Config.js`，并在编辑器里给出可改入口。
**源码里出现魔数就是待改的债。**

同一技能在不同地图上可能表现为数值/机制不同，所以技能参数要留地图级覆写的余地
（见 `MapSystem` 的 `_params` 注入）。

### 0.4 改了期望常量，必须在提交信息里逐项报告

用户明确要求：「随改更新被影响的期望常量，每项在提交里报告」。
写清**哪个常量、从什么改成什么、为什么**。没改也要写"本次未改动任何期望常量"。

## 二、架构与数据流

```
CONFIG（+ 地图覆写 + 阵营覆写）
      ↓  schema/index.js 统一解析
   实体 baseStats
      ↓  + EffectRegistry 的效果  + WeatherSystem  + WorldState（昼夜/熵/龙魂）
   AttributeCalculator.calc()  →  最终属性（帧级缓存）
      ↓
   CombatSystem / LaneMovementSystem / …
      ↓
   presentation/*  （只读）
```

### 系统间禁止互相 import

耦合一律走 `EventBus`，或在 `WorldState.update()` 里**单向**求值。
需要跨系统联动时（例：水晶重建后补发龙魂），在 `main.js` 里监听事件来接，
不要让 `MapSystem` 去 import `DragonSystem`。

**例外：`src/data/` 下的纯数据模块可以被任何人 import。**
`waveComposition.js` / `dragonCurve.js` / `towerModels.js` 就是为此存在的——
它们是"引擎和编辑器必须看到同一份"的东西的家。

### 世界级耦合默认全关

`CONFIG.world.couplings.*` 每一条都是独立开关。新增耦合必须保证：
全关时属性与接入前**逐位一致**（`tests/sim_world.mjs`、`tests/sim_entropy.mjs`
的第一条断言就是这个）。

当前默认：`dayNight: true`（用户定稿：白天小兵占优、夜晚防御塔占优），其余三条 false。

## 三、会静默出错的规则

这些违反了**不会报错**，只会让行为悄悄变样，所以格外危险。

### 3.1 渲染层不许往实体上写字段

渲染状态一律放渲染层自己的 entry / `WeakMap`
（见 `EffectsLayer` 的 `_beamEndY`、`UnitLayer` entry 上的 `ringHot`/`ringWant`）。
往实体上挂 `_renderXxx` 会污染逻辑层的序列化、克隆、存档，
而且沙盒/对战两套流程下生命周期不一致。

### 3.2 空间网格改了实体集合就要 `markDirty()`

`EntityContainer._grid` 是缓存。改了实体的存活/位置/增删而不失效它，
`findInRadius` 会返回过期结果。

**踩过的坑**：塔废墟不阻挡敌人，一开始判成"避障半径没乘可视缩放"。
真正的原因是**网格只索引存活实体**，所以 `findInRadius(..., aliveOnly=false)` 是空头支票，
废墟避障那段代码**从来没执行过**。
诊断时不要只看调用点的参数，要确认数据源里真的有那些数据。

### 3.3 缓存键必须包含影响结果的一切

`AttributeCalculator` 有帧级缓存，键里含天气版本与世界状态。
新增任何会改属性的全局量，**必须**同时进缓存键。
（曾经算出了 `sKey` 却忘了拼进 `cacheKey`，昼夜切换后属性纹丝不动。）

### 3.4 动画相位用挂钟时间，逻辑用 `gameTime`

`gameTime` 会被暂停/倍速影响。渲染的呼吸/闪烁若用它，暂停时会僵住或跳变。

### 3.5 同一个量只能有一个取值口

这是本仓库**最贵的一条**，反复出事：

| 事故 | 症状 |
|---|---|
| 塔层级解析被抄了四份 | 编辑器改了不生效 |
| 昼夜相位两处各读一份 | HUD 显示"夜晚"但塔灯永远不亮 |
| 属性页首屏与切页各写一份 | 同一个面板前后给出两个答案 |
| 排队力已存在，我差点又写第二份 | （及时发现）|

**做法**：把解析/计算抽成一个函数放进 `src/data/`，引擎和 UI 都 import 它。
新增"编辑器要预览引擎行为"的功能时，第一件事是问：**这个计算现在在哪？能不能直接调？**

### 3.6 `dt` 累加的浮点误差

`dt` 是 `1/30` 这种二进制表示不精确的数，累加 30 次得到 `0.9999999999999999`。
朴素的 `t < every` 会**每个周期都少触发一次**（"每秒一次"变成"每 1.03 秒一次"且持续漂移）。

```js
if (t < every - 1e-9) { timer = t; continue; }   // 留 epsilon
timer = t - every;                               // 减掉一个周期，保留余量，不要清 0
```

同理：**不要用 `(t*30) % 30 === 0` 判断"每秒"**，浮点误差会让它随机漏检。用帧计数器。

### 3.7 死配置

"定义了但全仓库无人读取"的配置项。它们的危害是：一旦被编辑器摆出来，
用户改多少都没反应，而且不报任何错。

**已清理**：七个 `dragonXxx` 键（旧公式遗物）。
**保留但有断言守着**：`battleTotemFromWave` / `battleTotemInterval`
（仅为兼容旧存档，`tests/sim_tplio.mjs` 断言全仓无读取点，**不要新增读取点**）。

加配置前先问：**引擎里真的有代码读它吗？**

## 四、配置与编辑器

**症状"编辑器改了不生效"在本项目出现过多次，根因都是同一个：编辑器写 A、运行时读 B。**

规矩：**取值/写值只走 `src/data/schema/index.js`**。
`towerTierBase` / `towerTierEffective` / `towerTierSource` 都在那里。

分层塔的叠加顺序（后者覆盖前者）：

```
CONFIG.templates.tower
  → 地图 tierStats[tier]
  → CONFIG.towerTierOverrides[tier]          （共享覆写）
  → CONFIG.factionOverrides[阵营].tower_<tier>（阵营覆写）
```

编辑器里每个字段都带**来源角标**（`towerTierSource`），悬停能看到完整叠加链和被压住的层——
排查"我改了怎么没变"先看这个。

新增可编辑分组时，把组名加进 `templateIO.js` 的 `IO_GROUPS`，
导出/导入/回归三边会自动跟上（**不要**在别处再抄一份键名列表）。

### 模板编辑器的页面注册表

### 编辑器怎么拆的（v43 P1-4）

编辑器本来是**一个 2919 行的对象字面量**。拆的时候用了它自身的一个性质：
**任意一段连续的顶层条目本身就是合法的对象字面量体**。于是按文件里已有的分节
切成七块，每块 `export const XXX = { ...原样... }`，方法体逐字未动、缩进未动，
`AttributeEditor.js` 里 `Object.assign({}, ...七块)` 合回同一个对象。

关键结论：**合并后仍然是一个对象**，所以跨块的 `this._renderPage(...)`、
`this._applyScope` 与拆分前完全一致，没有引入任何模块边界。

拆完之后有两条要守住的规矩：

1. **块与块之间不能有重复键**。`Object.assign` 遇到重复键会让后者静默覆盖前者 ——
   不报错，只是少一个方法。`sim_v43` 里"编③"钉住这件事。
2. **块不能反向 `import` AttributeEditor.js**（会成环）。需要往编辑器对象上挂
   运行期字段时一律用 `this.`。拆的时候真踩到过一次：`_newCustomStackKey`
   原本按名字写 `AttributeEditor._customEffectSeq`。

另外，凡是"读编辑器源码做断言"的测试都必须读**整片**（`_harness.mjs` 的
`editorSrc()`）。只读 `AttributeEditor.js` 的话，`!src.includes(X)` 这种否定断言
会因为"X 搬到隔壁文件去了"而假通过 —— 本仓库的经典空断言形状，见 §8.2。

面板长什么样由 `AttributeEditor._TPL_PAGES` **单向推导**：左树条目、页签、
作用域条出不出现、【应用】按钮写到哪。每页声明 `{ faction, apply, action, writes }`。

**为什么必须由页面自己声明**：改版前每一页都无条件画出【阵营】和【应用范围】两条作用域条，
而真读它们的只有四页。在"建筑体积"页把阵营切到🔴仅红方再改尺寸，
改的是双方共享的 `CONFIG.buildingSizes`，面板却写着"仅红方"。
**控件摆在那儿却不起作用，比没有这个控件糟得多——它让人相信了一件假事。**

### 出兵编排

对战出兵**只**由 `CONFIG.gameRules.laneWaveComposition` 决定（数组顺序 = 出兵先后），
经 `src/data/waveComposition.js` 的 `buildWaveOrder()` 求值——编辑器预览与真实出兵
共用这一个函数。

- 阵营可有独立编排（`CONFIG.factionOverrides[阵营].laneWaveComposition`），
  **整体替换不合并**（编排的顺序就是语义）；空数组视为"没配"，回退共享。
- 条件（`when`）来自 `WAVE_CONDITIONS` 注册表，41 条。加新条件**只改这张表**。
- 判定所需的世界快照由 `LaneWaveSystem` 每波组装一次（不是每条规则各查一遍）。
  **拿不到快照时一律放行**——宁可多出兵，也不要一条规则静默失效却不报错。
- `gameRules` 里的 `waveXxxCount` / `waveXxxInterval` 只影响**沙盒模式**。

## 五、自制内容（用户"自己做一个"）

**"改现有东西的数值"和"做出一件原本不存在的东西"是两套机制，别混。**

| 类型 | 存在哪 | 是什么 | 难点 |
|---|---|---|---|
| 状态 | `CONFIG.customEffects[id]` | 纯数据蓝图 | 无 |
| 兵种 | `CONFIG.customMinions[id]` | 模板数据 | 缺的字段从 `melee` 兜底；外观走 `minionStyle()` |
| 技能/武器 | `CONFIG.customSkills[id]` | **声明式规格** | 由 `behaviorVM` 编译成 `{onHit,onFrame,…}` |

载入靠 `customContent.syncAll()`（启动时 + 每次导入存档后各调一次，**幂等**）。
状态/兵种是数据；**技能不是**——引擎读的是 SkillLibrary 里的函数形状，
自制技能必须编译并注册，这一步不做就是"存档里有、用起来没有"。

### 为什么技能用声明式而不是让用户写代码

`eval` / `new Function` 这条路**不要走**：存档会变成可执行代码（导入别人的配置
等于运行别人的程序）、闭包无法序列化、报错抛在引擎深处。
所以技能是一段 JSON：`触发 → 条件 → 动作`，由 `src/core/behaviorVM.js` 解释。

**加新能力只改 `behaviorVM.js` 的 `TRIGGERS` / `CONDITIONS` / `ACTIONS` 三张表**，
所有已存的自制技能自动能用新原语。这三张表**同时是编辑器该显示哪些选项的唯一来源**。

诚实的边界：自制技能**只能做原语覆盖到的事**。内置 5 把武器里，爆炸/腐蚀/狙击
可以完整用原语表达；闪电杖和穿透型依赖渲染层与充能状态机，在原语之外。

### 两条硬规矩

1. **校验在保存时做完，不要留到运行时。** 技能每帧跑几百次。
   报错信息要指出**第几条规则、哪个字段、合法取值是什么**——`invalid spec` 等于没提示。
2. **删除要连带清理。** 删状态前查有没有技能在用它；删技能要从 `SkillLibrary._registry` 摘掉；
   删兵种要清掉出兵编排里引用它的规则（否则 `buildWaveOrder` 拿到不存在的类型，
   创建时静默返回 null，表现是"这一波莫名少了几个兵"）。

### 已知的坑

- **自制兵种的外观**：`MINION_STYLE` 里没有它。各处**统一走 `minionStyle(type)`**，
  不要写 `MINION_STYLE[type] || {...}`——那个 fallback 的图标是 ❓。
- **兵种类型列表不要写死**：编辑器用 `allMinionTypes()`。
  写死的话自制兵在界面上根本看不见 = 等于没做出来。
- **`onFrame` 的签名是 `(entityId, dt, instance, ctx)`**——这是 CombatSystem 的调用约定。
  写错顺序会让 `instance` 收到一个数字，赋值属性在 ESM 严格模式下直接抛异常。

| `howling_abyss_v1` | 嚎哭深渊 | 2325² | 1 | 外塔 + 水晶塔 + 召唤水晶 + 枢纽塔×2 + 水晶枢纽 |
| `twisted_treeline_v1` | 扭曲丛林 | 3000×1400 | 2 | 每路（外塔+内塔+召唤水晶）+ 枢纽塔 + 水晶枢纽 |

### 六.2 做一张新地图

1. 参照 `src/data/maps/twisted_treeline.js`（结构最清晰的一份）。
2. **必须声明 `world: {w,h}`**——相机自适应与边界绘制都依赖它。
3. **基地不在世界角点上就必须声明 `baseCenters`**（见 §6.4）。
4. 在 `src/data/maps/index.js` 里 import 并加入 `MAPS`。
5. `node tests/sim_maps.mjs` 会自动把新图纳入几何检查。
6. `node tools/balance_matrix.mjs --map <id> --runs 2 --minutes 10` 跑真实对局。

**照着参考图做图时，先量再画。** 扭曲丛林第一版把形状做**反**了：真图是花生形
（两端基地叶宽、腰部窄），我做成了柳叶眼形（两端窄、中间宽）。中间本该是狭窄的
遭遇战区，成了全图最开阔的地方。小地图上量得清清楚楚——兵线到中轴的距离
基地端 123px、腰部 73px——但凭印象画就是会画反。

没有图像库也能量：仓库里没有 PIL/ffmpeg-webp，但 `/opt/pw-browsers/chromium`
能解 webp。起一个 node http 静态服务（`file://` 会污染 canvas，getImageData 会抛），
用 `chromium --headless --dump-dom` 跑一个把 `getImageData` 结果打成文本的页面，
就能逐列采样出兵线中心线。全过程零 npm 依赖。

### 六.3 塔位不要手填 xy

**按【沿兵线的弧长】算出来。** 手填的坏处是"塔离兵线多远、相邻塔间距多少"全靠肉眼。

已经吃过一次亏：旧的 `midlane_v1` 用几何规则算外塔位置算错了，
**双方外塔越过中线互换了半区**——肉眼看画面完全正常，是跑仿真才发现的（该图已删除）。

`tests/sim_maps.mjs` 钉住的几何约束：

- 双方建筑构成完全对称；每方恰好一个水晶枢纽
- 所有建筑在世界范围内
- 分路建筑在走廊半宽或基地圈内（否则塔会立在墙里：小兵打不到它、它却能打小兵）
- 同一方同一路上**不同档位**的相邻攻击塔间距 > 2×射程（射程圈不重叠）
  - 同档位的一对（枢纽双塔）**刻意贴在一起**，不受此限
- 双方外塔各在自己半区，中间留有战斗区
- **基地圈必须罩住自家水晶枢纽**（圆心默认是世界角点，见 §6.4）

### 六.4 可行走判定

两套模型，二选一：

- **走廊模型**（默认）：可走 = 各兵线走廊（`walls.corridorHalfWidth`）∪ 双方基地圈（`baseOpenRadius`）。
- **navgrid**（只有峡谷用）：256×256 位图 base64 编进地图模块，是该图的唯一判据。

⚠️ `baseOpenRadius` 决定基地那块开阔地有多大。嚎哭深渊原来是 788 —— 每方一块直径 1576 的
广场，那不是"窄桥横跨深渊"，是"两个广场中间连了根线"。改地图时对着
`assets/maps/` 里的参考图确认这个数。

⚠️⚠️ **基地圈的圆心不是水晶枢纽，默认是【世界角点】**（蓝=左下、红=右上）。
这一条坑过两次，两次都是"注释里算的和代码里算的不是同一个基准点"：

- 我把嚎哭深渊的 `baseOpenRadius` 从 788 改到 300，注释写"枢纽塔在 d≤130 处，装得下"——
  那个 130 是**离水晶枢纽**的距离，而圈心是角点，枢纽塔离角点 360。300 的圈一座塔都装不下。
  正确值 460：塔（360）在圈内、离圈沿 100，两侧墙角离塔 149 ≤ 射程 180。
- 扭曲丛林的基地在地图左右两侧的**中点**，按角点算，基地圈会整个被甩到 (0,1400) 的空地上。

所以：**基地不在世界角点上的地图，必须声明 `baseCenters: { blue:{x,y}, red:{x,y} }`**。
取值口只有一个：`src/data/baseCircle.js` 的 `baseCircleCenter(map, faction)`
（`MapSystem` 与 `TerrainLayer` 都调它）。`sim_maps.mjs` 有一条通用断言钉住
"基地圈必须罩住自家水晶枢纽"，圆心搞错会当场红。

**`gateTier`：守着基地开口的是哪一档塔。** 峡谷是水晶塔（`base`），嚎哭深渊重做后
水晶塔挪到桥上了，把口的换成枢纽塔（`hq_tower`）。v34/v36/v37 那几条"入口落在塔射程内"
的几何断言按这个字段找塔，不再写死 `'base'`。**没有这种形态的地图就不要声明**——
扭曲丛林两条路在基地口就分岔、每方只有 1 座枢纽塔，一座塔封不住两个口，
那是编制决定的，不是"没做到"。

### 六.5 改地形要同时失效三样缓存

`MapSystem._nav`、`_laneField` 回流场、地形贴图与植被/水面。
目前这三处的失效通知是分散的，**动地形之前应先收敛成一个 `mapSystem.invalidate([...])`**。

### 六.6 小兵寻路

走廊内用引导向量，卡住时用 BFS 回流场（`_laneField`）脱困。
**注意源半径是 50，不是走廊半宽 130**——用 130 会把偏离中线 70px 的凹角标成距离 0
（"你已经到家了"），回流场直接失效。这个坑让脱困成功率从 8/30 卡了很久。

**排队感**：`LaneMovementSystem._steer` 里有一段"向走廊中心线回归"的力
（`CONFIG.tuning.laneCentering`）。它必须在三种情况下**让位**：附近有敌人、
正面被锚定障碍挡住、绕行黏性期内。不让位的后果各有对应用例会红（见附录）。

## 七、渲染层

### 7.1 Three.js 的光照单位

r155 起 `PointLight.intensity` 是**坎德拉**，地面照度 = `intensity / d^decay`。

**这里栽过两次**：

1. 把坎德拉当成照度填，写了 `0.66` —— 150px 处照度约 `3e-5`，而场景方向光是 `2.3`。
   差 5 个数量级，画面上完全看不见，表现为"这功能没做"。
2. 灯挂在空中 `ly` 高处时，地面上半径 `R` 那一点离灯是 `√(R²+ly²)`。
   `distance` 若按 `R` 给，超出的部分被 Three 截成 0 —— **灯抬得越高地面越黑**。

正确口径：填"地面边缘想剩多少照度"，代码按 `intensity = edgeLux × 斜距^decay` 反推。

**中心/边缘照度比 = `(斜距/灯高)^decay`**。灯挂太低时这个比值是 8.8 倍，
塔身必然先过曝——只要调到地面够亮，塔身一定是白的。抬高灯位才是解法，不是调亮。

### 7.2 光源数量必须恒定

Three 的前向渲染把光源数量编进着色器，**数量一变就要重编译所有材质**。
所以塔灯是**固定大小的池**（`CONFIG.ui.towerLight.poolSize`），
只改位置/强度/距离，用不到的把 `intensity` 设 0。

### 7.3 不要做"假光"

曾经加过一层地面辉光贴片给够不上灯池的塔补观感。它**不参与光照计算**，
照不亮任何东西，只是在地上涂了几坨白，用户直接问"高地上那一坨白的是啥"。
**更糟的是它掩盖了真问题**——真光源当时依然弱到照不亮地形，
而画面上"有亮的东西"让人以为成了。

**宁可少一层，也不要假的。**

### 7.4 躺平的几何体要 `DoubleSide`

`rotateX(-Math.PI/2)` 会把三角绕序翻过来，单面材质下从上往下看正好是背面、整层被剔掉。
诊断时 instanceCount / 属性 / shader 查下来全是对的，唯独想不到是绕序。

### 7.5 子节点会继承父节点的旋转

水晶粒子是水晶 Mesh 的子节点，默认和水晶严丝合缝地一起转。
要让两者相对转动，得给子节点**相对**角速度：

```
子节点世界角速度 = 父角速度 + 子自身角速度
→ 想要世界转速 ptsSpin，自身要转 (ptsSpin − spin)
```

直接把子节点转速设成目标值是错的——它的世界转速会变成两者之和。

## 八、测试规范

### 8.1 测什么

- **纯逻辑优先直接调产品代码**。例：射程圈强度函数只依赖 CONFIG + 传入的 deps，
  测试里把方法从源码里借出来直接调，逐档比对。
  **不要在测试里抄一份公式**——抄的那份永远会通过。
- **浏览器里测不了的就别硬测**。射程圈的渐显曾试过在浏览器里量：
  沙盒的移动/分离力会把钉住的小兵推走，探测又有 0.25s 节流，
  读到的距离和探测时的距离经常不是同一个，数值乱跳。**那种测法即使通过也说明不了任何事。**
- **纯渲染的东西靠 headless Chromium 实拍核对**，测试里只断言"配置软编码"与"实现走对了路"。

### 8.2 断言要钉行为形状，不要钉具体数字

射程圈的渐显阈值最初写死在断言里（50/10）。一调带宽三条断言当场全红——
但产品并没有坏。**断言该钉的是**：外圈 0、内圈 1、中点约一半、随距离单调递增。
阈值本身从 CONFIG 读。

### 8.3 参数化不许偷偷改行为

把写死的公式搬进配置时，**默认值必须与原式可证明等价**，并用断言钉住
（例：排队力参数化后，采样 3 万点断言 `weight=0.275/rampTo=70` 与 v39 原式逐位相同）。
这样"参数化"和"调参数"是两件能分开审的事。

### 8.4 不要拟合噪声

`tests/sim_wall.mjs` 的"近战全部越过兵墙"在 5/6 与 6/6 之间**随参数微调来回跳且不单调**。
选参数的标准是"在它通过的那些档里挑最好的"，而不是调到它刚好通过。

### 8.5 调参要先量分布

排队力第一版死区取 34，完全没效果——实测偏移的中位数只有 9~21px，
**整个差异都发生在死区以内**，力压根没机会启动。
凭直觉设阈值就会这样，**一定要先量分布再定阈值**。

## 九、调平衡

```bash
node tools/balance_matrix.mjs                           # 基线（峡谷）
node tools/balance_matrix.mjs --map twisted_treeline_v1 # 指定地图
node tools/balance_matrix.mjs --runs 20 --minutes 40    # 要下结论就用这个
node tools/balance_matrix.mjs --sweep dayNight          # 扫昼夜加成
node tools/balance_matrix.mjs --json out.json           # 落盘便于前后对比
```

它跑的是**真实**的 `MapSystem`/`LaneWaveSystem`/`CombatSystem`，不是简化模型。同一命令可复现。

**判读要点**：基线对局 40 分钟内**基本打不出胜负**，所以主信号是**推进度差**而不是胜率。
推进度 = 已打掉的档位数（外1/内2/高地3/召唤水晶4/枢纽5）+ 最前线那座的掉血比例。

**n=2~3 分不开信号与噪声。** 工具自己的判读提示写着"要下结论请用 `--runs 20` 以上"。
少量样本只能用来做"没有量级突变"的体检。

**不要自己临时写简易脚手架来量。** 试过一次，量出来"塔零掉血"，
连峡谷也是零——说明是脚手架没接全，那种数据说明不了任何事。用 `balance_matrix`。

## 附录：事故档案

按"症状 → 真因"整理。查问题时可以先在这里找同类。

| 症状 | 真因 |
|---|---|
| 编辑器改了不生效 | 塔层级解析被抄了四份，只改了其中一处 |
| 塔废墟不阻挡敌人 | 空间网格只索引存活实体，`aliveOnly=false` 是空头支票 |
| 塔废墟点了没反应 | 命中检测放行了，`UIManager.selectEntity` 那一句没放行 |

| 塔的发光"没实现" | 把坎德拉当照度填，差 5 个数量级 |
