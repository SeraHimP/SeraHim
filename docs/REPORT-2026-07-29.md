## 0. 先说三件必须先认的事

### 0.1 我上一轮对「废墟穿模」的诊断是错的

上一轮我把废墟穿模归因为「避障半径少乘了模型视觉放大系数 1.25」，并据此改了
`LaneMovementSystem` 和 `CONFIG.towerVizScale`。

**这个诊断是错的，那段代码根本就没有执行过。**

真正的原因见 Q3。我改的那段避障逻辑位于：

```js
for (const o of this.entities.findInRadius(minion.pos.x, minion.pos.y, rSelf + 80, ['tower'], false))
```

而 `EntityContainer.rebuildGridIfNeeded()` 里写着：

```js
for (const e of this._entities.values()) {
  if (!e.alive || !e.pos) continue;   // ← 死亡实体根本不进空间网格
  ...
}
```

`findInRadius` 走的是空间网格，第五个参数 `aliveOnly=false` 是**空头支票**——网格里压根没有
死亡实体，传什么都拿不到。所以「任意塔废墟 = 硬障碍」这段从写下来那天起就是死代码。

讽刺的是，这件事在代码库里**已经被写明过一次**了。`CanvasController._handleSelectClick`
的注释里白纸黑字：

> 必须单独扫描——空间网格【只索引活体】（rebuildGridIfNeeded 里 `if (!e.alive) continue`），
> 所以给 findInRadius 传 aliveOnly=false 是空头支票，永远拿不到幽灵。这就是"点不到"的根因。

同一个坑，点选那边踩过并写了注释，避障这边照样踩。我没有先搜这条注释就动手，
是我的失误。**上一轮 `towerVizScale` 那个改动建议回滚**（它不解决问题，只是多引入了一份耦合）。

### 0.2 视觉调参的协作方式需要改

这轮闪电杖光束我改了三次（重做 → 软边 → 收窄 → 回退），每次都是我猜、你看、你否。
我在这个环境里看不到实时画面，截图验证的成本又极高（这轮为了定位一个塔的屏幕坐标，

比"我猜一版 → 你否 → 我再猜"快一个数量级，也省额度。

### 0.3 「回归失败集 md5」这个基线本身是坏味道

我们一直用「失败断言集合的 md5 不变」当验收标准，现在长期挂着 **6 个失败项**：

```
✗ WeatherPanel 已挂到 window 供设置面板调用
✗ WeatherSystem 已挂到 window 供设置面板调用
✗ main.js 顶层无"先用后声明"（TDZ）
✗ 主循环：速度倍率只放大投喂时间（SIM_DT 不变，判定一致）
✗ 互卡死锁：确定性让位力存在
✗ 结构保护盾牌显式锁定不透明实色（修"透明"问题）
```

带着已知失败跑回归，等于把「红灯」当成了「基准色」——新引入的失败只能靠 md5 变化发现，
而 md5 一变还得人肉去比对是哪条。**这 6 条要么修掉、要么明确标记为 skip 并写明原因**，
让绿色重新意味着绿色。这件事我建议排进去，成本不高（大部分看着是断言写法过时）。

## Q1　弹道残留与错位

### 现象
1. 闪电杖攻击的目标死亡后，光束残留一段时间；
2. 残留的光束**位置错位**；
3. 穿透弹同理：目标死亡后残余弹道异常。

### 根因（三条，互相叠加）

**① 残留本身是"设计如此"，不是 bug。**
`ProjectileSystem` 的光束按 `attackerId` 存在 `this.beams` 里，武器每帧调 `fireBeam` 刷新。
目标死亡 → 武器 onFrame 提前 return → 不再刷新 → 进入 0.35s 淡出后删除。
`weapons.js` 里的注释明确写着这是刻意保留的：

> 目标【死亡】时不走这里（无新目标），残留淡出保留。

所以第一个要你拍板的是：**目标死亡后到底要不要残留？** 我倾向于「要，但要短且要冻结」，
理由见 ③。

**② 错位的真正机制：渲染层用"世界坐标"反查高度，而不是用"实体"。**

`EffectsLayer` 画光束时，两端的高度是这么来的：

```js
const sy = MY(b.startX, b.startY), ey = MY(b.endX, b.endY) * 0.6;
```

`MY` 就是 `UnitLayer.muzzleY(x, z, r = 26)`，它的实现是**按坐标就近搜索当前被跟踪的单位**：

```js
muzzleY(x, z, r = 26) {
  let best = 0, bestD = r * r;
  for (const [id, en] of this.map) {
    const dx = en.unit.position.x - x, dz = en.unit.position.z - z;
    if (dx*dx + dz*dz < bestD) { bestD = ...; best = (en.groundY||0) + (en.muzzleY||en.topY||0); }
  }
  return best;   // ← 附近没有单位时返回 0
}
```

于是目标一死、从 `UnitLayer.map` 里移除的那一帧：

- **最好的情况**：附近没别的单位 → `muzzleY` 返回 **0** → 光束末端高度从"目标炮口高"
  **瞬间掉到地面**。这就是你看到的"错位/跳一下"。
- **更糟的情况**：26 世界单位内还站着别的单位（混战时这是常态）→ `muzzleY`
  **搜到别人身上**，末端高度取成了另一个单位的炮口高 → 光束歪到一个毫不相干的高度上。

这不是参数没调好，是**抽象错了**：`muzzleY(x, z)` 是位置查询，但调用方要的是"这个实体的高度"。
位置查询在实体消失或有邻居时必然给出错误答案。

**③ 穿透弹是同一个病的另一种表现。**

子弹的飞行高度是这样插值的：

```js
const tgtE = entities?.get?.(p.targetId);
let by = my;                       // my = 出膛时的炮口高度
if (tgtE?.pos) {
  const tot = ...;                 // 全程距离
  const done = ...;                // 已飞行比例
  by = my + (MY(tgtE.pos.x, tgtE.pos.y) * 0.6 - my) * done;
}
```

目标死亡后 `entities.get()` 拿不到实体 → `tgtE` 为 null → **`by` 退化为常量 `my`**
→ 子弹从"沿弹道逐渐下降"突变成"水平飞行"。这正是"弹道异常"。

而我上一轮为了修 Q2「命中后拖尾瞬间消失」加的余烬淡出，**继承了这个错误高度**：
余烬的尾端高度 `ty` 用同一套插值算，目标没了就一起塌到 `my` → 余烬也错位。
（也就是说我上一轮那个改动让这个问题更显眼了。）

### 建议修法（三步，从根上治）

| 步骤 | 内容 | 风险 |
|---|---|---|
| ①（必做） | `muzzleY` 增加**按实体 id 查询**的重载：`muzzleYOf(entityId)`。光束/子弹记录 `targetId`，渲染时优先按 id 取。 | 低，纯新增 |
| ②（必做） | **端点高度快照**：光束/子弹在目标死亡的那一刻把端点坐标与端点高度冻结进自身对象，淡出期间不再重算。查不到实体就用快照，而不是回落到 0 或就近搜索。 | 低 |
| ③（需你拍板） | 残留策略：<br>**A** 目标死亡立刻 `clearBeam`，零残留；<br>**B** 保留 0.35s 但冻结（推荐）；<br>**C** 缩短到 0.12s 并快速淡出。 | 纯观感，随时可调 |

顺带：`muzzleY` 每帧对每条光束/每颗子弹做一次**全量遍历**所有被跟踪单位
（`for (const [id, en] of this.map)`），同屏 90+ 单位 × 几十发子弹 = 每帧数千次距离计算。
改成按 id 查表后这块开销直接归零，属于白捡的性能。

## Q2　模板编辑器重做

### 我对现状的坦率评价

`src/ui/AttributeEditor.js` 现在 **1973 行**，一个文件里塞了：
实体编辑、模板编辑、武器、被动技能、状态效果、龙魂、建筑体积、生成规则、出兵顺序、
对战成长、屠戮参数、三种作用域、阵营筛选、六个塔层级。**这是个上帝对象**，
而且这轮下来它还在继续膨胀（我自己往里加了成长和屠戮两组）。

### 你说的「生成顺序和生成规则冲突或重合」——完全正确，我确认这是真问题

两个 tab 的职责是**交叉**的，不是并列的：

| | 生成规则 tab | 出兵顺序 tab |
|---|---|---|
| 兵种开关 `spawnEnabled` | ✅ 在这里改 | ✅ 这里也读（关掉的整行标灰） |
| 数量 | ✅ `waveMeleeCount` 等 | ✅ 每条规则的 `count` |
| 周期 | ✅ `waveSiegeInterval` 等 | ✅ 每条规则的 `everyN` |
| 起始波次 | ✅ `ramMinWave` 等 | ✅ 每条规则的 `fromWave` |
| 实际对战生效的是哪个？ | ❌ **只影响沙盒模式** | ✅ **对战模式只认这个** |

也就是说：**「生成规则」里那些数量/间隔字段，在对战模式下全是摆设**，
真正决定对战出兵的只有 `laneWaveComposition`。面板上却把它们并排放着、
还都写着"修改后立即影响后续波次"。这是**误导性 UI**，你会照着改半天发现没反应——
这跟你之前报的「改武器不生效」是同一类病：**编辑器写 A、运行时读 B**。

顺便说，这类事故这轮已经发生**三次**了：
1. 分层塔被动 —— 编辑器写 `templates.tower._templateSkills`，运行时读硬编码；
2. 分层塔武器 —— 编辑器写 `templates.tower._templateWeapon`，运行时读地图字段；
3. 生成规则 —— 编辑器写 `gameRules.wave*Count`，对战运行时读 `laneWaveComposition`。

三次同类事故说明这不是手滑，是**缺少"编辑器字段 ↔ 运行时读取点"的强制绑定机制**。

### 重构方案：Schema 驱动的统一编辑器

抛开现有结构，我建议这么做（这也顺带解决 Q5）：

**核心思想：把"什么可编辑"从 UI 代码里抽出来，变成一份数据（Schema），UI 由 Schema 生成。**

```
src/data/schema/
  index.js          — 注册表：把所有可编辑对象登记在一起
  towerSchema.js    — 塔（六层级）：属性 / 武器 / 被动 / 状态 / 龙魂 / 体积
  minionSchema.js   — 小兵（八兵种）：属性 / 被动 / 成长 / 屠戮
  waveSchema.js     — 出兵编排（唯一真源，吞掉现在的"生成规则"）
  mapSchema.js      — 地图：路点 / 建筑摆位 / 地形 / 河道 / 坑位
  worldSchema.js    — 世界：天气 / 昼夜 / 熵 / 龙魂（见 Q4）
```

每个字段的 Schema 条目长这样：

```js
{
  key: 'attackDamage',
  label: '攻击力',
  type: 'number', min: 0, max: 2000, step: 1,
  // 关键：读写路径显式声明 —— 编辑器和运行时【共用同一个存取器】
  get: (ctx) => resolveTowerStat(ctx.tier, ctx.faction, 'attackDamage'),
  set: (ctx, v) => writeTowerOverride(ctx.tier, ctx.faction, 'attackDamage', v),
  scope: ['template', 'field'],       // 这个字段支持哪些应用范围
  affects: '新生成的塔 + 可选场上已有塔',
}
```

**这么做直接解决三件事：**

1. **「编辑器写 A、运行时读 B」从结构上不可能再发生**——因为 `get/set` 就是运行时用的那对存取器。
   可以再加一条回归测试：遍历 Schema，对每个字段做「写入 → 生成一个单位 → 读回」，
   不一致就红灯。这条测试能一次性钉死上面那三类事故。
2. **UI 自动生成**，`AttributeEditor.js` 从 1973 行缩到几百行（只剩渲染器 + 交互），
   新增可编辑项 = 加一条 Schema，不用碰 UI 代码。
3. **作用域不再每个 tab 重复**——「仅模板 / 仅场上 / 两者 × 阵营」提到**全局工具栏**，
   由 Schema 的 `scope` 字段决定哪些控件在当前作用域下可用（不可用的直接灰掉并给出原因）。

### 面板结构重排（解决"乱七八糟"）

```
┌─ 工具栏（常驻）：应用范围 [仅模板|仅场上|两者]　阵营 [双方|蓝|红]　[重置本页] [导出/导入 JSON]
├─ 左侧树：
│   🏰 防御塔 ─ 外塔 / 内塔 / 水晶塔 / 枢纽塔 / 召唤水晶 / 水晶枢纽
│   ⚔️ 小兵   ─ 近战 / 远程 / 炮兵 / 超级 / 图腾 / 术士 / 蚀骨 / 攻城车
│   🐉 巨龙   ─ 各元素 / 远古龙 / 龙魂
│   🌊 出兵编排（唯一真源，吞掉旧"生成规则"）
│   🗺️ 地图   ─ 路点 / 建筑摆位 / 地形 / 河道 / 坑位
│   🌍 世界   ─ 天气 / 昼夜 / 熵 / 平衡总控
└─ 右侧：属性 | 武器 | 被动 | 状态 | 龙魂 | 高级
```

要点：
- **删掉「生成规则」tab**，把兵种开关合并进「出兵编排」的每一行（一个眼睛图标）。
  沙盒模式的数量/间隔单独放到「世界 → 沙盒」下，不和对战混。
- 每个字段旁标注**当前值的来源**（出厂 / 地图覆写 / 模板覆写 / 阵营覆写），
  点一下能"还原到上一层"。现在的覆写有四层，不可视化根本没法调。
- **导出/导入 JSON**：整套配置可存档、可分享、可版本对比。这个功能成本很低但收益极大，
  你调平衡时可以存多套方案来回切。

## Q3　废墟穿模 + 死亡塔应可选中

### 根因（已定位，见 §0.1）

`EntityContainer` 的空间网格**只索引活体**，导致所有走 `findInRadius` 的"死亡实体"查询
全部失效。受影响的至少有两处：

- `LaneMovementSystem._steer` 的废墟避障 → **从未生效**，所以小兵一直穿废墟；
- 任何未来想做的"对废墟/幽灵的范围查询"都会踩同一个坑。

### 建议修法

**方案 A（推荐）：网格索引扩展到"静态障碍"**

```js
// rebuildGridIfNeeded
if (!e.pos) continue;
if (!e.alive && !e._ruin && !e._respawnAt) continue;   // 废墟/待重生水晶进网格
```

代价：网格里多几十个条目（全图最多 30 座塔）。所有 `aliveOnly=true` 的调用点行为不变
（那层过滤在 `findInRadius` 里还在）。这是最小改动且一次性根治。

**方案 B：单独维护静态障碍列表**
塔与废墟数量极少（≤30），单开一个数组全量扫描，零网格改动。更保守但多一份状态要同步。

我倾向 **A**，因为它同时把"点选幽灵要单独全量扫描"那段 hack 也一并消灭了。

### 死亡塔可选中 / 可编辑

`CanvasController._handleSelectClick` 目前只补扫了 `_respawnAt` 幽灵：

```js
for (const e of ents.getAllTowers(false)) {
  if (!e.alive && e._respawnAt) consider(e);   // ← 没有 _ruin
}
```

按方案 A 改完网格后，这段 hack 可以直接删掉，废墟自然可选中。

你要的「设置阵营、属性、是否存活」需要在实体编辑器里新增一组**运维操作**：

| 操作 | 说明 |
|---|---|
| 复活 / 击杀 | `alive` 切换 + 清除/打上 `_ruin` + 通知渲染层重建视觉 + 重算结构保护 |
| 改阵营 | 改 `_mapFaction`/`faction` + 刷新模型颜色 + 清空当前目标（否则会继续打原队友） |
| 改层级 | 改 `_mapTier` + 重新解析该层级的属性/被动/武器 |
| 属性 | 已有，但对死亡单位当前是禁用的，要放开 |

⚠️ 有几处**副作用**必须一起处理，否则会出灵异 bug：
- `isStructureProtected` 按"上一层建筑是否存活"判定 → 复活/击杀会连锁改变别的塔的保护状态；
- `MapSystem` 的水晶重生队列 `_respawnQueue` 持有引用 → 手动复活要把队列项撤掉；
- 计分 `CTX.__score` 在塔死亡时 +1 → 手动复活要不要 -1？（我建议：手动操作不计分，
  并在日志里标注"[编辑器]"以示区分）

## Q4　天气 / 昼夜 / 熵 / 龙魂 —— 统一重做

### 现状盘点（诚实版）

| 系统 | 代码状态 | 实际效果 |
|---|---|---|
| 天气 | `WeatherSystem` 662 行，OU 随机过程 + softmax 权重 + 极端天气充能，机制相当完整 | ✅ 通过 `getModifiers` 给单位加成，**真的在生效** |
| 昼夜 | `DayNight.js` 只做光照关键帧 | ❌ **纯视觉，零数值影响**。我之前接的只是"随天气开关联动"和 6 分钟周期 |
| 熵 | **只有设计文档，零实现** | ❌ 完全没有 |
| 龙魂 | 技能定义齐全（8 种魂），`DragonSystem` 311 行 | ⚠️ 有击杀→解锁，但你定的"6 条龙 + ≥4 击杀才成魂、都不到 4 则无魂、之后出远古龙"这套规则**没实现** |

**最大的结构问题：这四个系统各自为政，没有一个共同的"世界状态"层。**
天气直接改单位属性、昼夜只改光照、熵不存在、龙魂走技能系统。
想做"白天蓝方有优势、夜晚红方有优势"或者"熵值改变天气分布"这类联动，
现在没有任何地方可以挂。

### 建议架构：引入 `WorldState` 聚合层

```
                    ┌──────────────────────────────┐
                    │        WorldState            │  ← 唯一的"世界当前长什么样"
                    │  weather: {权重, 极端, 强度}  │
                    │  daynight: {相位 0..1, 是否夜}│
                    │  entropy:  {黑核, 白核, 红核} │
                    │  souls:    {blue:[], red:[]} │
                    └──────────────┬───────────────┘
                                   │ getModifiers(entity) → 一张合并后的修正表
                                   ▼
                         AttributeCalculator
```

**要点：**

1. **单一出口**。所有世界级修正只从 `WorldState.getModifiers(entity)` 出，
   不再有"天气一条路、龙魂另一条路"。调试时一个断点看得到全部来源。
2. **可解释**。配套 `getBreakdown(entity)` 返回逐项来源（"雨 -8% 攻速 / 夜晚 红方 +5% 移速 /
   熵红核 +12% 伤害波动"），直接喂给 UI 的属性面板。现在天气已经有 `getModifierBreakdown`，
   把它提升为全系统的规范。
3. **互相影响走"输入→输出"而不是互相调用**：
   - 熵 → 天气：熵值调制 `WeatherSystem` 的 `mu`（均值回复目标），熵越高极端天气越频繁；
   - 熵 → 昼夜：高熵时夜晚变长（相位速度非线性）；
   - 龙魂 → 熵：击杀龙降低己方侧的熵（秩序压制混乱）；
   - 昼夜 → 阵营：白天蓝方 +X%、夜晚红方 +X%（你定的非对称）。
   全部在 `WorldState.update()` 里单向求值，**禁止系统之间互相 import**。
4. **每个耦合项独立开关**（你之前定的规矩）：`CONFIG.world.couplings = { entropyToWeather: true, ... }`，
   关掉任意一条系统仍能自洽运行。

### 平衡性上的顾虑（要提前说）

引入熵之后是**非对称对战**，而目前的数值全部是对称的（双方同模板同成长）。
非对称平衡的验证成本比对称高一个量级——不能只看"谁赢"，要看**胜率曲线随熵值的变化**。
建议配一个 headless 批量模拟脚本：固定种子跑 N 局 × M 个熵档位，输出胜率/时长/推塔进度矩阵。
否则调一次数值就得人肉看一局，根本不可能收敛。这个脚本我认为是**熵系统开工的前置条件**。

## Q5　全面编辑器（地图 / 小兵 / 塔 / 龙魂 / 一切）

这一条和 Q2 是同一件事的两个面，用同一套 Schema 机制就能吃下。这里只补**地图编辑器**——
它是唯一需要新交互范式的部分。

### 地图编辑器（新增，工作量最大）

| 能力 | 说明 | 难度 |
|---|---|---|
| 建筑摆位 | 拖拽塔/水晶，实时显示射程圈与重叠检查 | 中 |
| 路点编辑 | 拖拽/增删兵线折线控制点，实时重算回流场 | 中 |
| 地形刷 | 笔刷编辑 navgrid 可走位图（可走/墙），带撤销 | 高 |
| 河道 | 调 `riverHalfWidth` / 起止 / 深度，实时预览 | 低 |
| 坑位 | 拖拽龙坑/男爵坑，改半径与深度 | 低 |
| 导出 | 导出成 `src/data/maps/xxx.js` 可直接落盘的地图模块 | 中 |

⚠️ 有个**必须注意的坑**：navgrid 是 256×256 位图，编码进 JS 模块（base64）。
笔刷编辑要在内存位图上改，**同时失效三样东西**：`MapSystem._nav` 缓存、
`_laneField` 回流场缓存、地形贴图与植被/水面。这三处的失效通知现在是分散的，
做地图编辑器之前应该先收敛成一个 `mapSystem.invalidate(['nav','field','terrain'])`。

## 附：其它我认为该说的问题（你让我畅所欲言）

1. **`window` 被当成事实上的服务总线。**
   `window.__three` / `window.CTX` / `window.__app` / `window.__weather` / `window.__gridOn` /
   `window.__terrainAvoid` / `window.__laneFlow` …… 渲染层直接读 `window.gameTime`，
   系统层直接读 `window.__towerRules`。这让"谁依赖谁"完全不可见，也让 headless 测试
   必须先手工搭一个假 window。`GameContext` 本来是为收敛它而建的，但它自己也只是
   "同步到 window"的转发器，没真正收口。建议至少给新增项立规矩：一律走 CTX，不再新增裸 `window.__xxx`。

2. **`EffectsLayer.js` 正在变成第二个上帝对象**（已 700 行，含 Batch 图元库 + 7 类特效 +
   腐蚀波纹 + 拖尾余烬）。图元库（`Batch`）应该独立成文件，特效按类别拆。

3. **技能系统的 `_params` 注入链条很脆。**
   这轮我发现地图覆写只对有 `onFrame` 的技能生效（屠戮只有 `onHit`，所以它的 `instance._params`
   永远是 undefined）。已修，但同类问题可能还有——`onHit`/`onBeingAttacked`/`onEquip`
   这几条路径的 ctx 内容并不一致，建议统一成一个 `SkillContext` 工厂。

4. **没有"配置健全性检查"。**
   现在改坏一个数（比如把攻速设成 0）不会有任何警告，要等你在游戏里发现塔不开火。
   Schema 里有 min/max 之后，可以顺手加一个启动期自检 + 编辑器实时校验。

5. **`CollisionSystem` 完全不处理塔与建筑**，所有的塔避障都塞在 `LaneMovementSystem._steer` 里，
   和小兵间的分离力、绕行、让位混在同一个 200 行的函数里。这个函数已经很难改了
   （里面有五套互相牵制的力：期望/分离/绕行/回归/让位）。建议把"对静态障碍的避让"
   整体移到 `CollisionSystem`，`_steer` 只管单位之间。

6. **升温（heat）机制的可见性存疑。**
   穿透弹有个 `heat` 0..1 会改变颜色/尺寸/拖尾，但玩家没有任何界面能看到"当前升温几层"。
   要么给它一个 UI（塔的状态栏），要么承认它只是视觉噪音并简化掉。

7. **回归测试里有 3 个用例是在断言 `main.js` 的源码文本**（正则匹配源文件字符串）。
   这轮我已经把其中 4 条改成读真值了，但这种"测源码文本"的写法还有残留
   （比如 `sim_abyss.mjs` 里断言 `CombatSystem.js` 包含某个字符串）。
   它们会在任何无害重构时误报，属于负资产。
