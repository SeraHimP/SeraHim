## 一、LoL 官方机制核实（WebSearch 查证，非凭记忆）

结论：**"法强1:1转化为攻击力"这个提法本身混淆了 LoL 里两个不同名字相近的机制**，
需要先分清楚，才能判断我们现在实现的是哪一个、对不对。

### 1.1 Adaptive Force（自适应之力）—— 一种"装备/符文给的中间态属性"

来源：Rageblade、征服者主宰等少数装备/符文，给的不是直接的 AD 或 AP，而是一份
"自适应之力"，**结算时**才决定变成哪个：

> 比较【总法强】与【额外攻击力】（不含基础攻击力，只算装备/符文给的部分）哪个大：
> - 法强更多 → 1 点自适应之力 = **1.0 点法强**
> - 额外攻击力更多 → 1 点自适应之力 = **0.6 点额外攻击力**

**这个转化比例本来就不是 1:1**——换成法强是 1:1，换成攻击力是打 6 折（0.6:1）。
这是 Riot 故意设计的不对称：自适应之力"更值钱"的方向是法强，换成攻击力要打折，
背后逻辑是攻击力类装备通常还顺带给穿甲/暴击/攻速等副属性，单纯的攻击力数值本身
不该跟法强等价交换。

我们仓库里 `AttributeCalculator.js` 的 `adaptiveForce` 处理**已经是对的**，逐字对应：
```js
if (goToAP) stats.abilityPower = ap + af;        // 换法强：1:1
else stats.attackDamage = ad + af * 0.6;          // 换攻击力：打 6 折
```
这部分不用改。

### 1.2 Adaptive Damage（自适应伤害）—— 某个技能/效果的伤害类型怎么判定

跟上面完全是两回事。指的是"某个技能的伤害算出来之后，算物理还是算魔法"：

> 伤害类型由【这次伤害里 AD 贡献的部分】和【AP 贡献的部分】谁大谁小决定——
> AD 贡献更大就算物理伤害，AP 贡献更大就算魔法伤害，贡献相等时按该效果自己
> 定义的默认类型。

关键点：**原始技能公式本身有自己的 AD 系数和 AP 系数**（比如某技能"50+0.4×攻击力
+0.5×法强"，两个系数是这个技能自己定的，不是恒为1），伤害总量 = 两项系数各自算出来
的数相加，"贡献大小"只是拿来决定扣防御还是扣魔抗，不影响伤害总量怎么算。

**我们的处境**：这个游戏没有"每个技能一条自己的公式"，每个单位只有一个笼统的
`attackDamage`/`abilityPower` 两个数。上一轮（Q3）参考 LoL 这条规则时，用户拍板
"A，照搬LOL"，实现成了：
```js
hitInfo.baseDamage = attackType === 'adaptive' ? attackDamage + abilityPower : attackDamage;
```
即：AD 系数和 AP 系数都取 1.0（两项相加），伤害类型按 `attackDamage` 和
`abilityPower` 谁大判物理/魔法。这是"没有真实技能公式时最接近 LoL 精神"的一种
简化，但**跟 LoL 真实情况不同的地方**是：LoL 里两个系数是**该技能自己定的**、
经常不是 1:1（比如很多技能是 0.5×AD 或 0.6×AP 这种"打折"系数），我们这里等于
把系数**全都焊死成 1.0**——这不是"抄错了"，是"没有单独系数可抄，只能选一个统一
系数"，但代价是：**任何单位只要同时有 AD 又有 AP，就会比"只有其中一种"的同类
单位额外多拿一截白给的伤害**，因为两边都按满系数 1.0 计入总伤害，不存在"取更大
的那个、丢弃另一个"这种事。这正是下面第二节要排查的"异常强大"的一个主要来源。

## 二、为什么小兵现在"异常强大"——排查结论

不是单独哪一行代码写错了，是**两个各自看起来合理的改动叠在一起**产生了复利：

### 2.1 改动 A（a1d31f8，本轮更早）：所有单位默认改成 `attackType: 'adaptive'`

现在 `CONFIG.templates` 里**全部 9 个模板**（melee/ranged/siege/super/totem/
warlock/corrupt/ram/tower，连 dragon 也是）都是 `attackType: 'adaptive'`。

### 2.2 改动 B（同一轮）：`adaptive` 类型的伤害 = `attackDamage + abilityPower`（相加，不是二选一）

见上面 1.2 节。

### 2.3 改动 C（更早一轮，v51.3）：大型小兵（siege/super/ram/totem/warlock/corrupt）
在 `battleGrowth` 里各自加了一条 `ap: 0.5`/波成长

```js
siege:   { hp: 10, ad: 0.9,   res: 0.30, ap: 0.5 },
super:   { hp: 20, ad: 1.875, res: 0.15, ap: 0.5 },
ram:     { hp: 10, ad: 0.1,   res: 0,    ap: 0.5 },
totem:   { hp: 8,  ad: 0.375, res: 0.1,  ap: 0.5 },
warlock: { hp: 8,  ad: 0.375, res: 0.1,  ap: 0.5 },
corrupt: { hp: 8,  ad: 0.375, res: 0.1,  ap: 0.5 },
```
这条本身是有历史原因的（"法强成长"最初是给塔设计的，后来大型小兵也顺带给了一条），
单独看不算错。

### 2.4 三条叠加的结果

A+B+C 加在一起：**任何一个"大型小兵"，只要 AD 成长和 AP 成长同时存在，它的
真实输出伤害就是"AD 那条成长曲线 + AP 那条成长曲线"两条一起算进总伤害**，而不是
传统意义上"这个兵是物理输出，AP 对它没用"那种非此即彼。换句话说，这些兵种现在
的有效成长速率，比数值面板上单看 `ad` 那一列的成长率要快得多（相当于双份成长）。

### 2.5 具体到每个兵种的裸身基线数值（未装备任何武器/技能，仅模板+成长起点）

| 兵种 | AD（基础） | AP（基础） | AP 成长/波 | AD 成长/波 | 当前 attackType 结算 | 当前总伤害（基线） |
|---|---|---|---|---|---|---|
| melee 近战 | 9 | 0（无字段） | 无 | 0.3 | 物理（AP恒0，AD胜出） | 9（不受影响，符合目标） |
| ranged 远程 | 6.5 | **10** | 无 | 0.375 | 魔法（AP10>AD6.5，基线成立，但没有ap成长，AD涨着涨着迟早反超变回物理） | 6.5+10=**16.5**（比只算6.5多了10） |
| siege 炮兵 | 15 | 0 | 0.5 | 0.9 | 物理（基线AP0），但AP会一直涨 | 15（基线），随波次AP也加进总伤害 |
| super 超级兵 | 208 | 0 | 0.5 | 1.875 | 物理（AD巨大，AP短期内追不上） | 208（基线），AP growth 也算进去 |
| totem 图腾兵 | 7.5 | **8** | 0.5 | 0.375 | 魔法（AP8>AD7.5） | 7.5+8=**15.5**（快翻倍） |
| warlock 术士兵 | **1**（刻意压到接近0） | **30** | 0.5 | 0.375 | 魔法（AP远大于AD） | 1+30=**31**（AD虽然只有1，但AP=30整个吃满还叠加成长） |
| corrupt 蚀骨兵 | 13 | 0 | 0.5 | 0.375 | 物理（基线），AP慢慢追上来 | 13（基线），AP growth 一起加 |
| ram 攻城车 | 70 | 0 | 0.5 | 0.1（极慢） | 物理（AD远大于AP，长期都不会翻） | 70（基线），AP growth 加成占比很小 |
| tower 裸塔 | 152 | 0 | （塔走独立的 66.7% 比例成长，非 battleGrowth） | — | 物理 | 152（不受本节这套 battleGrowth 影响） |

**最典型的问题案例是 warlock（术士兵）**：AD 被刻意压到 1（几乎是"名义上还留着"），
本意是让它靠 AP=30 吃满魔法伤害；但因为伤害公式是相加不是二选一，它现在的真实
基线伤害是 **1+30=31**，而不是设计意图里"这是个魔法伤害兵，伤害应该主要看这个
AP=30 怎么用"——AP 相当于变成了"直接加算的额外攻击力"，而不是"决定它打魔法这件事
本身"。totem（图腾兵）同理，AP=8 是白给的额外伤害。

## 四、核心待决策问题（这些决定了具体怎么改，需要用户先拍板，不是我能替用户定的）

1. **"AD+AP相加"这条公式本身要不要保留？** 这是这次"异常强大"的最大杠杆。
   两个方向：
   - **方向甲（贴近LoL真实机制）**：既然我们的技能公式没有真实的"AD系数/AP系数"，
     可以改成"取较大值"而不是"相加"（即传统意义上的"这个兵是物理输出或魔法输出，
     二选一，不叠加"）——这样"低AD+高AP"的兵就是纯魔法伤害（伤害数值=AP，不叠加
     AD那一点点），"低AP+高AD"就是纯物理，干净利落，且直接解决了本次异常强大的
     根因。但这样就不是真正的"自适应"了，更像是"根据AD/AP谁大就走哪种类型，但
     伤害只算那一种"——退回到了上上轮之前的旧逻辑（那次也是用户认可过的一版）。
   - **方向乙（保留相加，但用系数压低）**：继续用"AD+AP相加"，但给一个统一的
     折算系数（比如 `attackDamage×coefA + abilityPower×coefB`，coefA/coefB
     不恒为1，参考 LoL 技能常见系数量级如 0.5~0.7），这样"两边都有"依然会比
     "只有一边"强，但不会强这么多。更贴近 LoL 技能的真实观感（大多数技能系数
     确实不是1），但需要额外定两个新系数，且"这个系数具体多少"本身也是主观判断，
     需要平衡验证。
   
   两个方向我都可以做，需要你定这个方向再往下走数值。

2. **远程兵/图腾/术士/蚀骨要不要继续走"自适应"类型，还是干脆给它们写死
   `attackType: 'magic'`？** 用户原话"远程兵/术士/图腾/蚀骨攻击力极低，走魔法
   攻击"——如果目标就是"这几个兵种恒定是魔法伤害"，比起继续用自适应+人工把AD压得
   极低去"骗"自适应判定选中魔法，直接写死 `attackType: 'magic'` 更直接、不会
   出现"某天AD/AP某个数值调整后类型意外反转"的脆弱性。同理炮兵/超级兵可以直接写死
   `physical`。近战本来就已经是这个效果（AP恒0）。这样"自适应"这个类型就只留给
   塔（真的会根据装备武器变化）和少数希望动态变化的单位，语义更清楚。
   这个改动跟第1条是独立的两件事，可以分开决定。

3. **法强成长口径统一**：塔现在走"AD成长的66.7%"这条比例（上一轮刚定），小兵走
   `battleGrowth[type].ap` 这个独立的固定值/波——要不要统一成同一套逻辑（比如
   小兵也改成"AD成长的X%"），还是保留"塔和小兵本来就是两类东西，各自一套成长
   曲线"这个现状？如果决定砍掉/削弱某些兵种的AP成长（比如方向甲下，"低AD高AP"
   的magic兵种其实不需要AD成长很快，"高AD低AP"的物理兵种也不需要AP继续涨），
   具体每个兵种的成长数值要重新定一遍，需要你给出大方向（比如"魔法系小兵AD不
   成长/成长极慢，物理系小兵AP不成长"）后我再落地具体数字。

4. **是否需要重新跑一遍 balance_matrix**（`tools/balance_matrix.mjs`）验证改完
   之后的实际对局表现，而不是只看裸身数值？考虑到这次问题就是"看起来分开都合理，
   实际叠加跑起来才异常"，改完之后建议至少跑一轮批量模拟对比改动前后的实际强度，
   不能只靠数值表面判断。
