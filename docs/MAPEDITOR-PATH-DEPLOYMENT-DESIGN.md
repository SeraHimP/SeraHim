# 地图编辑器 + 兵路径自定义 + 出兵编排升级 —— 设计报告

> 交付形式说明：本文档**只是设计，不是实现**。用户原话："这个还是你认真构思，出报告，
> 明早起来我查看。" 里面没有一行改动过 `src/`。所有涉及"现状"的描述都标了具体文件/行号，
> 可以直接去核对；涉及"新做"的部分标了候选方案和取舍理由，而不是直接给答案——
> 有几处关键决策（§7）需要你来定，不是我能替你定的。

## 0. 结论先行

三件事（地图编辑器 / 兵路径自定义 / 出兵编排升级）**不是三个独立小功能，是一个地基
+ 两层楼**：

- **地基**：地图编辑器。当前所有地图是纯 JS 模块（`src/data/maps/*.js`），手填坐标、
  跑几何校验脚本、肉眼比对参考图——**零运行时编辑能力**。这是三件事里工作量最大、
  也是另外两件事必须依附的部分（路径要画在地图上，出兵编排里的"某档建筑"条件也要
  地图先有建筑数据）。
- **二层楼 A**：兵路径自定义。技术上是地图编辑器的一个"图层"（编辑 `lane.waypoints`
  数组），不是独立系统。
- **二层楼 B**：出兵编排升级。这个**现状比想象中成熟**——`CONFIG.gameRules.
  laneWaveComposition` + `src/data/waveComposition.js` 已经是一套声明式规则引擎，
  41 条条件、编辑器实时预览与真实出兵共用同一份求值函数（`buildWaveOrder`）。
  真正缺的只是**动作只有"刷兵"一种**，没有"改状态/加技能"。这条升级路径清楚，
  照着 `src/core/behaviorVM.js`（自制技能已经在用的"触发→条件→动作"声明式解释器）
  的模子做一遍即可，**不需要新发明一套机制**。

优先级建议（不是必须按这个顺序做，是"如果只能先做一件"时的建议）：
**出兵编排升级 > 地图编辑器 > 兵路径自定义**。理由见 §6 分阶段路线图——
出兵编排升级改动面最小、复用度最高、独立于另外两件事就能上线；
地图编辑器工作量最大但地基不稳的话兵路径编辑做出来也立不住；
兵路径自定义在没有地图编辑器之前，其实"改代码里的 waypoints 数组"已经能做到
（只是不能拖拽），优先级最低。

## 1. 现状盘点（每条都有出处）

### 1.1 地图数据长什么样

`src/data/maps/summoners_rift.js`（239 行）等三个文件，每张地图是一个具名导出的
**纯对象字面量**：`world:{w,h}`、`lanes:[{id, waypoints:[{x,y}...]}]`、
`buildings:[{faction,tier,laneId,pos,weapon}]`、`walls:{corridorHalfWidth}`、
`tierStats`、`skillOverrides`、`useNavgrid`、`dragon:{enabled}`、`pits`、
`heightZones`、`baseCircleRadius`/`baseOpenRadius`/`baseCenters`/`gateTier`。

登记在 `src/data/maps/index.js` 的 `MAPS` 常量里（`{[id]: 地图对象}`），
`MapSystem.loadMap(mapId, mode)` 按 id 取。**没有任何持久化/导入导出通道**——
新地图 = 新提交一个 `.js` 文件。

### 1.2 两套"可行走"判定模型（`docs/DEVELOPMENT.md` §6.4）

- **走廊模型**（默认）：可走 = 兵线折线 ± `corridorHalfWidth` 的带状区域 ∪ 双方
  `baseOpenRadius` 圆。纯公式，`MapSystem.isWalkable(x,y)` 现算。扭曲丛林/嚎哭深渊
  曾经也用过这套，现已弃用（见下条）。
- **navgrid**（召唤师峡谷、嚎哭深渊、扭曲丛林三张图都在用）：`{n:256, bits:'<base64>'}`
  ——256×256 网格、逐格 1 bit（可走/不可走）、按行 LSB 优先位打包再 base64。
  `MapSystem._navgrid()` 读 `this.currentMap.navgrid || SR_NAVGRID`。
  **这份位图完全在浏览器之外产生**：`src/data/maps/map_navgrids.js` 头注写得很清楚——
  拿参考图（`assets/maps/*.png`）→ Python/PIL 逐像素判色 → 闭运算去毛刺 → 连通块过滤
  → 位打包 → 手动粘贴 base64 字符串进源码。**这正是"地形刷"要替代的手工流程。**

两套模型二选一，走廊模型公式驱动无法表达"野区""河道""不规则墙体"这种自由形状——
navgrid 才是通用解，走廊模型只适合"三路对称"这种规则布局。**地图编辑器的地形刷
应该以 navgrid 为目标格式**，不要再往走廊模型上堆参数。

### 1.3 兵线路径（`lane.waypoints`）

一个 `{x,y}` 数组，`LaneMovementSystem.js` 沿它做"到达判定→切下一个点"的行军，
偏离走廊中心线时有一股"回归力"（`CONFIG.tuning.laneCentering`），卡住时用 navgrid
上的 BFS 回流场（`_laneField`）脱困。**这个字段现在只能改源码**，没有任何 UI。

塔位同理——`docs/DEVELOPMENT.md` §6.3 强调"塔位不要手填 xy，要按沿兵线弧长算"，
现在也是靠人（或我）用脚本量出来再手填坐标常量。

### 1.4 出兵编排现状（比想象中成熟）

`LaneWaveSystem.spawnWave()` 每波调 `buildWaveOrder(waveNumber, nexusDown, rules,
faction, ctx)`（`src/data/waveComposition.js`），后者读
`CONFIG.gameRules.laneWaveComposition`（一个规则数组，顺序即出兵顺序）。

每条规则形如 `{type, count, fromWave, everyN, when, whenArg}`：

- `type`：出哪种兵（含自制兵种，走 `spawnEnabled` 总开关）。
- `count` / `fromWave` / `everyN`：数量 + 起始波次 + 间隔波次。
- `when`：条件 token，查 `WAVE_CONDITIONS` 表——**41 条**，覆盖"游戏时间"
  （`time.after` / `time.before`）和"建筑状态"（我方/敌方 × 6 档建筑 × 全灭/部分被摧毁
  /全部完好，笛卡尔积自动生成）。

覆写体系是二维的（阵营 × 路），解析优先级"从具体到笼统"四层，写在
`compositionFor()` 一个函数里，出兵/编辑器预览/批量模拟三处共用，不会漂移。

**这套东西已经是"出兵编排"的完整骨架**，用户想要的"复杂多条件规则、引用任意模块
状态"里的"多条件"和"复杂"这两块，**表结构完全够用**，缺的是：

1. **条件来源只有"游戏时间"和"建筑状态"**，没有龙魂/天气/熵/得分差这些其它模块的状态。
2. **动作只有"刷 N 个某类型的兵"一种**，没有"给某方加 buff""触发某个技能""改法力"
   这类动作。
3. **UI 上一条规则=一次刷兵**，没有"同一触发条件下执行多个动作"的概念（虽然表结构
   稍加扩展就能表达）。

### 1.5 `behaviorVM.js`——现成的"声明式规则引擎"范式

`src/core/behaviorVM.js` 是自制技能/武器用的"触发(`TRIGGERS`) → 条件(`CONDITIONS`)
→ 动作(`ACTIONS`)"解释器，JSON 规格、保存时校验（`validateSpec`，逐条报错到"第几条
规则第几个动作"）、编译成引擎认识的 `{onHit,onFrame,onEquip,...}` 钩子。**这正是
"出兵编排升级"要抄的模子**——不是另起一套，是把同一个模式套用在"关卡/对局级事件"
而不是"单位战斗事件"上。

两者的差别只在**触发时机的粒度**：`behaviorVM` 的触发是"命中时/每隔一段时间/装备时
/被攻击时"（单位级、每帧可能跑几百次，所以校验必须前置），出兵编排要的触发是
"每波开始时/建筑被摧毁时/龙被击杀时/游戏进行到某时刻"（对局级、频率低得多，
一局几十次量级）。**两套引擎不应该合并**（粒度不同、需要的 ctx 不同），但**校验/
编译/JSON 规格这套骨架应该照抄**。

### 1.6 自制内容的存储/持久化范式

`src/data/customContent.js`：`CONFIG.customEffects/customSkills/customMinions[id]`，
纯数据自动进存档（因为整个 `CONFIG` 都会被序列化），技能类需要额外"编译并注册"
一步（`syncAll()`，启动时 + 每次导入存档后调用，**必须幂等**）。

`docs/DEVELOPMENT.md` §5 的"已知的坑"里点名过两条会直接坑到地图编辑器：
- **列表不要写死**：自制兵种如果哪里写死了 `MINION_STYLE[...]` 而不是走
  `allMinionTypes()`，就会"做出来了但界面上看不见"。地图选择器同理，必须遍历
  `{...MAPS, ...CONFIG.customMaps}`，不能只读 `MAPS`。
- **删除要连带清理**：删一张自制地图，出兵编排里按 `laneId` 引用它的路的规则、
  `factionOverrides` 里按 mapId 存的覆写都要一并清，否则读到"不存在的路"会静默出错。

## 2. 设计总纲：三件事共享的原则

1. **唯一真源函数**（现有代码里反复强调、反复踩坑的教训）：编辑器预览用的求值逻辑
   与运行时真实生效的逻辑必须是**同一个函数**。`buildWaveOrder` 已经做到了，
   新的地形校验、路径校验、编排动作执行都要照此办理——**不允许"编辑器里另写一份
   校验代码"**。
2. **声明式 + JSON，不 eval**：`behaviorVM.js` 头注说得很清楚，这条不再重复论证，
   直接沿用同一立场。
3. **保存时校验，报错到具体位置**：不要"存了、跑起来才发现某条规则是坏的"。
4. **软编码**（CLAUDE.md 硬约束）：地形刷笔刷大小、路径点吸附半径、编排条件里的
   数值阈值，全部进 `CONFIG`，编辑器里给入口，不要写成 JS 常量。
5. **和现有存档/导出机制对齐**：新数据（自制地图）走
   `CONFIG.customMaps[id]` + `templateIO.js` 的 `IO_GROUPS`/`CUSTOM_GROUPS`，
   不另起一套 localStorage key——否则"导出配置分享给别人"这个已有功能会漏掉地图。
6. **改地形要通知失效**（`docs/DEVELOPMENT.md` §6.5 已经点名的坑）：
   `MapSystem._nav`、`_laneField` 回流场、地形贴图与植被/水面，三处缓存现在是分散
   失效的。**地图编辑器动笔刷的那一刻，就是这个"应该收敛成一个 `invalidate()`"
   的技术债必须先还的时刻**——不然编辑器画完地形，游戏里看到的还是旧的。这是
   本报告认为**必须在地图编辑器开工前先做的一处重构**，不是可以拖到后面的小事。

## 3. 地图编辑器设计

### 3.1 编辑器形态：叠加在现有渲染层上的一个模式，不是新窗口

现有 3D 渲染（`ThreeRenderer`）已经用正交相机俯视整张地图，這正是地图编辑器需要的
视角。建议做成"进入编辑模式"（类似现在的"点击画布建塔"选位模式，
`canvasController.armPlaceMode`），而不是切到一个独立的 2D 网格编辑器页面——
理由是"所见即所得"：笔刷画完的地形要立刻套上真实的地形材质/植被/水面渲染看效果，
不能只在一张示意网格上画完再导入。

编辑模式下四个图层，靠左侧/顶部工具条切换（复用现有毛玻璃工具条视觉风格，
`docs/ui-standard.md` 已经定了这套规范，编辑器不要另开一套 UI 语言）：

- **地形层**：笔刷绘制可走/不可走（navgrid 位图）。
- **建筑层**：拖拽放置/移动塔、召唤水晶、枢纽；每个建筑一个属性面板
  （阵营/档位/所属路/武器），复用模板编辑器现有的字段定义，不新造一套。
- **路径层**：见 §4（兵路径自定义）。
- **区域层**：龙坑/男爵坑坑心、基地圈半径/圆心（`baseCenters`）、`gateTier`——
  这些是"点/半径"级别的少量参数，用表单而不是画笔更合适。

### 3.2 地形笔刷：写 navgrid，不写走廊模型

**核心技术问题：navgrid 现在的生产流程完全在浏览器外（Python/PIL），编辑器必须
在浏览器里重新实现"画布 → 位图 → 位打包 base64"这条链路，且不能引入新依赖
（项目零 npm 依赖、无构建步骤）。**

方案：

1. 编辑器内维护一张 `n×n`（默认沿用 256，可配置）的 `Uint8Array`（0/1），
   笔刷是"以鼠标位置为中心、半径 R 格"的圆形填充/擦除（软编码：
   `CONFIG.mapEditor.brushRadius` 默认值）。
2. 实时预览：用 `<canvas>` 的 `ImageData` 直接画（1 像素/格或按缩放插值），
   叠加在 3D 场景之上做半透明遮罩，不需要每笔都重建 Three.js 几何。
3. 保存时才做一次位打包（LSB 优先，逐格写比特，8 格一字节）+ `btoa()` 转 base64——
   这一步纯 JS，不需要 PIL，`sr_navgrid.js` 里的格式本来就是给 JS 运行时读的，
   编码端理应也能用 JS 实现（现在是 Python 只是因为原始数据来源是 PNG 参考图，
   编辑器场景下数据直接就在内存里，链路反而更短）。
4. **去毛刺**（现有 Python 流程里的"3×3 多数表决平滑 + 填洞 + 连通块过滤"）
   作为一个"整理"按钮而不是每笔自动跑——笔刷阶段用户想要的是所见即所得，
   自动平滑反而会让笔刷"不听话"；整理是画完之后的一次性操作，同样用纯 JS
   重实现这几个算法（都不复杂：多数表决是 3×3 卷积，连通块过滤是一次 BFS/
   Union-Find，填洞是"小于 N 格的孤立不可走块翻转"）。
5. **必须复用 `MapSystem.isWalkable` 同一套读取逻辑做实时校验**（§2 原则 1）：
   笔刷改完立刻跑 `tests/sim_maps.mjs` 里那几条几何约束的**同款判定函数**
   （不是重新写一遍，是把 `sim_maps.mjs` 里的纯校验逻辑抽出来做成
   `src/data/mapValidate.js` 共享模块，测试和编辑器都调它），红线实时标出
   "这里建筑被围进墙里了""基地圈没罩住水晶枢纽"。

### 3.3 手动画墙：是地形笔刷的一个特化操作，不是独立机制

用户原话"手动画画造墙"——建议不要做成"墙"和"地形"两套独立数据（那是在重复
"同一件事实现了两遍"，CLAUDE.md/DEVELOPMENT.md 反复强调的坑）。**墙 = 在 navgrid
上画一条"不可走"的线/路径**，笔刷工具提供两种模式：

- **自由笔刷**（圆形填充，见 3.2）——适合大片野区/河道。
- **画线/折线模式**（点击落点、连续点形成折线，按线宽展开成不可走带状区域）
  ——适合规则的墙体，比自由笔刷更精确、更适合"造一堵直墙"这种意图。

两者本质都是往同一个 `Uint8Array` 写 0，UI 只是取点方式不同，**不要在数据层
区分"墙"和"地形"**——这样"墙"和"地形"永远不会因为分开维护而出现"墙那份数据
和地形那份数据打架"（比如墙画在了地形认为可走的地方，两边各算各的碰撞）。

### 3.4 建筑摆放：吸附到路径，不是自由拖拽

`docs/DEVELOPMENT.md` §6.3 的教训（塔位手填导致双方外塔越界互换半区，肉眼看不出、
跑仿真才发现）直接决定了这里的设计：**建筑摆放不能是纯自由拖拽落点**。

建议交互：拖拽建筑图标到路径附近时，**自动吸附到"沿该路径的弧长位置"**（用户
可以再微调离路径的垂直偏移，但弧长位置由吸附决定），编辑器同步显示"与前一档同路
建筑的间距是否 > 2×射程"这类实时校验（复用 §3.2 的共享校验模块）。这样从交互层面
就杜绝了"手填坐标算错"这类问题，而不是事后靠测试脚本才发现。

### 3.5 持久化与登记

- 数据落在 `CONFIG.customMaps[id]`（结构与内置地图对象完全一致，`§1.1` 那些字段
  照抄，只是 `navgrid` 字段现在能在编辑器里生成而不必手填 base64）。
- `templateIO.js` 的 `IO_GROUPS` 加入 `customMaps`，导出/导入自动跟上。
- 地图选择 UI（`ModeDialog.js` 等）改成遍历 `{...MAPS, ...CONFIG.customMaps}`，
  不是只读 `MAPS`——这正是 §1.6 点名的"列表不要写死"那个坑。
- 删除自制地图要清理：出兵编排里按 `laneId` 引用它的规则、`factionOverrides`
  里存的地图专属覆写（如果以后做了地图级 `skillOverrides` 编辑）。

## 4. 兵路径自定义设计

作为地图编辑器的"路径层"，不是独立系统（§0 已说明）。

### 4.1 编辑操作

- **新增路径点**：在路径线段上双击插入一个新点（自动计算插入位置，不需要手选
  "插在第几个点后面"）。
- **删除路径点**：选中点后删除；**首尾两点不可删**（首点是水晶枢纽出兵点参考、
  末点是路径终点，`LaneMovementSystem`/`LaneWaveSystem._laneSpawnPoint` 都假设
  至少有两个点）。
- **拖拽移动点**：直接拖拽，实时重绘路径线与"走廊预览带"（若走廊模型）或
  "该点是否落在可走 navgrid 区域内"的校验标记（若 navgrid 模型——navgrid 地图
  的路径本质是"行军参考线"，不影响可走判定本身，但路径偏出可走区太远会导致
  小兵频繁触发脱困 BFS，属于"能跑但难看"的质量问题，编辑器应该给出黄色警告
  而不是硬拦）。
- **新增/删除整条路径（lane）**：地图路数不是固定 3 路（扭曲丛林 2 路、嚎哭深渊
  1 路），编辑器要支持任意路数，新增路径时要求同步创建双方对应的出兵点与至少
  一档建筑，否则"有路无兵""有路无塔"会在游戏里表现为静默的空路。

### 4.2 与出兵编排的联动

`WAVE_CONDITIONS` 里"本路/全场"的判定（`tally()` 函数）依赖 `STRUCT_TIERS`
按 `laneId` 查 `census.lanes[laneId]`——**新增一条路径后，出兵编排的条件下拉框
要能立刻识别这条新 `laneId`**，不需要额外注册（现有代码已经是"按 census 现查"
而不是写死路名列表，天然兼容，只需要地图编辑器保存时把新 `laneId` 一致地写进
`lanes`/`buildings`/`laneWaveCompositionByLane` 三处）。

### 4.3 与出兵点计算的联动（`_laneSpawnPoint`）

出兵点由"路径首点 + 沿首段方向外推 100px"现算（`LaneWaveSystem._laneSpawnPoint`），
**不需要单独编辑**——只要路径首点、次点位置合理（不要让首段方向指向墙里），
出兵点自动正确。编辑器可以在路径层直接叠加渲染这个推算出的出兵点位置作为参考，
帮助判断"这段路径方向会不会把兵生成在墙里"。

## 5. 出兵编排升级设计

### 5.1 数据结构扩展

现有规则 `{type, count, fromWave, everyN, when, whenArg}` 是"单一动作=刷兵"的
特化形式。建议**不推翻现有结构**（避免所有老配置失效），而是新增一种规则类型：

```js
// 现有：刷兵规则（保留，行为不变）
{ type: 'melee', count: 3, fromWave: 0, everyN: 1, when: '', whenArg: null }

// 新增：动作规则（当 kind:'action' 时，type 字段不再是兵种，走 do 数组）
{ kind: 'action', when: 'enemy.nexus_lane.allDown', whenArg: null,
  fromWave: 10, everyN: 5,
  do: [
    { act: 'applyEffect', to: 'faction', effect: 'rally_buff', duration: 20 },
    { act: 'spawnMinion', minionType: 'super', count: 1 },
  ] }
```

`do` 数组复用 `behaviorVM.js` 的 `ACTIONS` 表模式（同一个"动作表=校验来源=编辑器
选项来源"的原则，§2 原则 1），但**开一张新的 `WAVE_ACTIONS` 表**而不是直接摘
`behaviorVM.ACTIONS`——原因是执行上下文完全不同：`behaviorVM` 的动作作用于
"一个具体单位对另一个具体单位"（`self`/`target`），出兵编排的动作作用于
"一个阵营/一条路"（没有单一目标单位的概念，`to` 的取值应该是 `'faction'` /
`'lane'` 这种范围，不是具体实体）。两张表**结构相似、内容不同**，这是有意的
不复用（模式复用，数据不复用）。

### 5.2 条件来源扩展

`WAVE_CONDITIONS` 现在只有"时间"和"建筑状态"两组，来源是 `ctx = {faction, enemy,
laneId, gameTime, nexusDown, census}`（`LaneWaveSystem._enqueueForFaction` 现场
组装）。扩展方向：

- **龙魂/巨龙之力**：`ctx.dragonState = { soulOwner, factionKills, killCounts }`
  （从 `DragonSystem` 现有字段直接摘，不需要新计算）。条件例："我方已成魂"
  "敌方已集齐 ≥2 层某元素之力"。
- **天气/时段**：`ctx.weather`、`ctx.dayPhase`（从 `WeatherSystem`/`DayNight`
  现有状态摘）。条件例："当前是暴雨天气"。
- **得分差**：`ctx.score = CTX.__score`（已存在的计分板）。条件例："我方推塔数
  领先 ≥3 座"。
- **熵**（`EntropySystem`，`behaviorVM.js` 的搜索结果里也出现过这个系统，
  说明它已经有自己的 TRIGGERS/ACTIONS 风格接口，值得直接摘同款字段）。

**每加一组来源，只改 `ctx` 组装 + `WAVE_CONDITIONS` 表**，`whenPasses`/
`compositionFor`/UI 下拉框都自动跟上（这是现有代码已经做对的地方，新增不破坏
这个性质）。

### 5.3 UI 改动

现有"出兵顺序"面板（`pagesGameplayWorld.js` 附近，具体页面需要进一步定位，
本报告未深入到编辑器 UI 代码层）大概率是一个线性列表 + 表单。升级后每条规则
要能区分"刷兵"与"动作"两种卡片样式（不同图标/配色），"动作"卡片展开后是
`do` 数组的子列表，每个子项选动作类型后按 `WAVE_ACTIONS[act].fields` 现出对应
字段——这与 `behaviorVM` 已有的技能编辑器表单生成逻辑是同一个模式，UI 层的
表单生成代码理应能抽出公共部分复用（哪怕只是"根据 fields 数组生成表单控件"
这一小段）。

### 5.4 校验

复用 `behaviorVM.validateSpec` 的报错风格（"第几条规则、第几个动作、合法取值
是什么"），新写 `validateWaveComposition(rules)`，保存时跑，不要留到运行时
静默失效。

## 6. 分阶段实施路线图（建议，不是强制顺序）

**阶段一：出兵编排升级（独立可交付，风险最低）**
1. `WAVE_ACTIONS` 表 + 规则结构扩展（`kind:'action'`）。
2. `ctx` 扩展龙魂/天气/得分来源。
3. UI 表单化 + 校验。
4. `tests/sim_waveaction.mjs`：新增动作规则的求值断言，钉行为形状（见 §8）。

**阶段二：地形/缓存失效重构（地基前置工作，§2 原则 6 点名的技术债）**
1. 抽出 `mapSystem.invalidate([...])`，收敛现有三处分散失效。
2. 抽出 `src/data/mapValidate.js`（把 `sim_maps.mjs` 里的几何校验逻辑做成可复用
   的纯函数），测试改成调用它而不是自己重复一份判定——这一步顺手把"编辑器和测试
   共用同一份校验"的地基先打好，不用等编辑器动工才做。

**阶段三：地图编辑器 MVP**
1. navgrid 笔刷（画/擦，不含去毛刺整理）+ 保存/加载。
2. 建筑摆放（拖拽 + 弧长吸附）。
3. `CONFIG.customMaps` 持久化 + 地图选择 UI 接入。
4. 实时校验红线（调阶段二的共享模块）。

**阶段四：地图编辑器完善**
1. 画线/折线造墙模式。
2. 去毛刺整理按钮。
3. 龙坑/基地圈等"点/半径"参数表单。

**阶段五：兵路径自定义**
1. 路径层的增删拖拽点。
2. 与出兵编排 `laneId` 联动校验（新路径必须配齐兵种/建筑，否则给警告）。

理由：路径编辑单独看技术难度不高，但**没有地图编辑器的地基（画布交互框架、
共享校验、持久化通道），路径编辑做出来也是孤立的一小块**——排在最后不是因为
不重要，是因为它复用阶段三/四打好的基础设施成本最低。

## 7. 需要你确认的开放问题

1. **navgrid 分辨率**：现在固定 256×256。地图编辑器如果支持"新建任意大小的地图"，
   分辨率要不要跟着 `world.w/h` 的比例自适应，还是继续固定 256（更大的图会导致
   每格代表的实际距离变粗，笔刷精度下降）？
2. **地形笔刷要不要支持"高度"**（`heightZones` 那套台阶地形现在是几个比例参数
   算出来的，不是逐格数据）？如果笔刷只管可走性，高度还是维持"少数几个全局参数"
   的老办法，两者数据模型不统一，你能接受吗？
3. **出兵编排的动作范围要放多宽**：§5.1 的例子只给了"施加状态"和"额外刷兵"。
   要不要开放"直接调用某个已有 behaviorVM 技能的动作序列"（相当于两套引擎打通）？
   这会让动作表达力大增，但也让两套引擎的边界变模糊，需要你权衡。
4. **地图编辑器要不要做"多人协作/云端存档"**：当前项目是纯静态站、零后端，
   `CONFIG.customMaps` 只能存在浏览器本地（localStorage）+ 手动导出 JSON 分享。
   如果以后要支持"我做的地图发给你玩"，现在这套导出/导入机制已经够用，只是
   体验是"发文件"不是"发链接"，要不要现在就规划得更长远一点？
